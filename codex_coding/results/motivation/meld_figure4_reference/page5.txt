Overview
3.1 Observations and Insights
Meld is motivated by two insights. First, disentangling de-
pendency via SM-level cooperation. Modern GPUs’ on-chip
interconnects provide sufficient bandwidth and fine-grained
synchronization, transforming the GPU into a cooperative
system with highly flexible state exchange across the SMs.
6Blackwell relaxes this with a fallback size, but constraints persist (§4.2).
This unlocks fine-grained SM cooperation: by decomposing
coarse-grained, kernel-level dependencies into sub-task-level
ones, it transforms traditional multi-kernel execution into
flexible, sub-task-level pipelines. It also enables absorption
of redundant memory traffic with cooperative loading.
This SM cooperation further unlocks just-in-time reduc-
tion. Leveraging hardware-offloaded asynchronous trans-
mission and signaling (§2.4), the intermediate states can be
asynchronously delivered to the target SM’s shared memory,
ready before they are needed for reduction (i.e., just-in-time).
Once the target SM finishes its sub-task, it performs the re-
duction directly within its local SRAM in a wait-free manner,
thereby further enhancing pipeline efficiency.
Second, dynamic coordination via decoupled execution.
Existing programming frameworks fail to adapt to dynamic
workloads due to the coupling of computation logic and hard-
ware mapping. This inherent coupling constrains general-
purpose frameworks (e.g., Triton) to static parallelism (e.g.,
split-K), while restricting expert-optimized kernels to uni-
form tiling strategies. With decoupled programming and
execution, developers declaratively define the computation
logic, while the runtime dynamically determines paralleliza-
tion and cooperation strategies according to input shapes.
Together, these two insights enable cross-SM kernel fusion
for GPU programs with dynamic workloads. As Fig. 3 (d)
shows, after finishing a split-KV sub-task, instead of mate-
rializing the intermediate results, the producer SM (asyn-
chronously) forwards them to the consumer SM’s shared
memory and proceeds to the next sub-task, while the con-
sumer SM performs reduction directly. The hardware barri-
ers (mbarrier) ensure pipeline correctness. With decoupled
execution, the runtime dynamically adapts the parallelization
and cooperation plan to input shapes. This dynamic coop-
eration further enables adaptive copy absorption. In many
cases, multiple SMs load identical data, e.g., many sequences
share a prefix in attention [68–71], and multiple SMs load
the same hidden states (GEMM-1) and intermediate states
(GEMM-2) in MoE forward. Via on-chip interconnects, we
use one SM to load data and broadcast it to others.
