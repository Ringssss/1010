2. 【整体任务信息 —— FLUIDCKPT 在做什么】

**使命**：让一个已经加载并后处理完毕的模型实例，在多节点集群中作为**可流动、可保活的对象**
存在，使任意节点都能在远低于冷启动的时间内把它拉起来。流动面覆盖 SSD / DRAM / HBM。

**问题定义**：GLM-5.3 从"进程不存在"到"可以服务"是分钟级冷启动，而现实需求
（A/B 测试、多租户、故障转移、训练-推理交替）是秒级切换。一次切换付几分钟脚手架
代价不可接受。

**核心技术抽象**（详见 docx/cites/2026-09-27_fluidckpt_scope_and_positioning.md）：

- 模型实例 = 一组可寻址的存储对象（每个 TP rank 的每个参数，用 HIP IPC handle 标识，零拷贝）
  + 一份派生属性清单（post-processing 产生、无法从结构推断的量，如 MLA 的 w_kc/w_vc）。
- 流动 = 带容量约束的 max-flow。每条边是一段实测带宽，每个 rank 是 sink，keeper 是中间节点。

**POC 的三条边界（为什么收敛到这里）**：

1. 不走 NVMe 刷盘。本地 NVMe 2.5 GB/s、NFS 0.27 GB/s；703.7 GiB 走 NFS 是 47 分钟级。
   所以保活必须在 DRAM/HBM 层做，SSD 只作无其它副本时的兜底。
2. 不修改推理引擎源码。SGLang 在本环境是厂商深度定制版，改源码会让结果无法与官方对比，
   且随版本升级失效。因此用 **import 期 hook**（利用 SGLang spawn 的 re-import 语义）。
3. 只用集合通信。本 fabric 跨节点 send/recv 不可用，流动规划必须建模成集合通信问题——
   这正好与 max-flow 算法契合。

**硬件与模型**：

- node27/28/29 各 8 卡（gfx936，DTK），跨节点 fabric 只支持 collectives。
- 目标模型 GLM-5.3：GlmMoeDsaForCausalLM，**703.7 GiB**，78 层 + MTP=1，256 experts top-8，
  hidden 6144，fp8 e4m3 block[128,128]，tp_size=16，141 个 safetensors，118,629 个张量。
  路径：/data/node28/shared/zhujianian/GLM-5.3
- 备用模型 Qwen3.6-35B-A3B（已迁到 /data/node28/shared/zhujianian/Qwen3.6-35B-A3B，
  67G / 43 文件，26 个 safetensors，1045 条 weight_map）。**这个模型在 gfx936 上能跑起来。**

3. 当前技术阻塞（外部原因，不是我们的 bug —— 这一点必须记住）

**GLM-5.3 在本硬件上无法启动**，根因在 SGLang 自家 NSA path，与 FluidCKPT 无关。
已用**完全无 hook 的纯 `sglang.launch_server`**（FLUIDCKPT_MODE=""，进程 cmdline 与日志双重确认）
复现出**完全相同的**崩溃：20:03:43 启动 → 20:34:28 KERNEL VMFault（17 次），栈完全一致。

完整根因链：

1. `is_hcu()` 为 True（gfx936 在支持列表 ["gfx936","gfx938","gfx928"] 内）
2. `is_hcu_native_fp8_supported()` 要求字面量 `gfx938` → **恒为 False**
3. → `use_fp8_index_k_cache` 恒 False → `index_k_buffer_dtype = bfloat16`
4. → `_use_hcu_bf16_index_cache()` True → `_get_q_k_bf16`
5. → `lightop_attention.fuse_layernorm_rotary_embedding`（nsa_indexer.py:438）崩溃

**翻任何 flag 都绕不过去**：NSA 的**两条** HCU 分支都调用同一个 `_get_q_k_bf16`
（nsa_indexer.py:1573-1576），因此 `--kv-cache-dtype` 无法路由到别的路径。
vendor builtin 也不可内省（`inspect.signature` 报 no signature found for builtin），无 env 开关。

**平台本身是健康的**：同一硬件上 Qwen3.6 用 triton attention backend 成功 fired up
（2026-09-22 日志）；GLM-5.2 / GLM-5.3 **从未成功启动过**。

6. 关键机制洞察（canonical 账本：docx/context_index/04_insight_ledger.md，I1–I13）

**方向选择前必须先读这张表**，避免重走已排除的路。

- **I1**：per-tensor 逐张量集合通信被固定开销主导。每次广播 ~99.3 µs 固定成本，
  与字节数无关；256 次广播 = 25.43 ms 仅传 1.32 GB/s。**必须 bucketing**：
  同样字节打成 bucket 后 0.91 ms / 36.73 GB/s，**27.8× 提升**。
  ← **这是对 SGLang 逐张量远程加载的核心优势所在。**
  来源：results/bw/bucket_27_29_r8.json、src/bench/bucket_bw.py
- **I2**：跨节点 fabric 只支持 collectives。send/recv 报
  ncclSocketInit: connecting to address with family 0；collectives 正常。
  → 传输层设计只能用 broadcast/allgather/reduce-scatter。来源：results/diag/
- **I3**：跨节点聚合带宽远高于单流。单流 25.7 GB/s；8 rank/节点 N 流聚合 205.8 GB/s
  （64 MiB 时 230）。→ 规划器按聚合带宽估算，尽量多流并行。
  来源：results/bw/multi_rank_27_29_r8.json
- **I4**：单节点 tmpfs 装不下一个节点的 TP shard。/dev/shm 252 GiB < 8 rank × 44 GB = 352 GB。
  → per-node tmpfs 持久化不可行，保活必须落在 keeper 的 pinned DRAM。
- **I5**：gfx936 上 SGLang 的 fp8 index cache 恒不可用（见第 3 节根因链）。
  ← **GLM-5.3 无法启动的根因**，且 NSA 两条 HCU 分支共用 _get_q_k_bf16，翻 flag 无解。
- **I6**：权重字节高度集中在大张量上。118,629 个张量中，58,776 个（8–16 MiB）占 **97.9%** 字节；
  中位数仅 12 KiB。→ ~60,000 个小张量字节占比极小但个数极多，**正是 I1 的受害面**，
  bucketing 应优先合并它们。来源：results/model/glm53_tensor_sizes.json
- **I7**：HIP IPC 可零拷贝跨进程交接权重。t.untyped_storage()._share_cuda_() 返回 8-tuple，
  consumer 用 _new_shared_cuda(*h) + set_() 重建。→ keeper 与推理进程间不需经磁盘或 host 拷贝；
  consumer 峰值 HBM 仅 0.01 GiB。来源：src/transport/ipc_probe.py
- **I8**：spawn 启动模式让 import 期 hook 覆盖所有 worker。SGLang 用
  mp.set_start_method("spawn", force=True)，launcher 的 __main__ 在每个子进程重新 import。
  → **可以在不修改 SGLang 源码的前提下给全部 16 个 worker 装 hook。**
- **I9**：冷启动时间绝大部分与权重无关。122 s 端到端中权重读取仅 14.24 s（12%）；
  import 链 29.17 s（sgl_kernel 单模块 self time 14.47 s）；Load weight begin 前 41.2 s。
  → **修正过**：早期"保活只省 12%"的框架已被用户纠正。保活的正确定位是与"进程常驻"叠加，
  省掉整条 disk → decode → shard → quantize 路径。
- **I10**：NFS 是数量级更慢的通道。NFS 0.27 GB/s vs 本地 NVMe 2.5 GB/s vs H2D 46 GB/s
  vs 跨节点聚合 205.8 GB/s。→ 多节点权重分发绝不能走 NFS（GLM-5.3 量级是 47 分钟级）。
- **I11**：node27 的 H2D/D2H 对称且远快于本地盘。H2D 46 / D2H 47 GB/s，本地 NVMe 仅 2.5（约 18×）。
  → DRAM ↔ HBM 之间流动远比落盘便宜；SSD 层只作"无其它副本时"的兜底。
- **I12**：单节点资源模型在特定区间内精确，越界即失效。冻结的 V9 模型在 held-out 上
  median 4.4% / max 8.9%；但 V10 的"共享 PCIe switch 容量"假设被否决（拟合给它零容量，
  且 h2d + NVMe 合计 52 GB/s）。→ 规划器必须停留在单节点 root port、无 NUMA fan-out 的区间内；
  **同一 root port 跨两个 NUMA 节点会塌陷**（h2d 掉到 29.5）。
- **I13**：core dump 可单次耗尽整个 /home。core_pattern=core、core_uses_pid=1，
  内核对每个崩溃 GPU 进程 dump 整个显存；8 卡 = 8 × 18–22 GB ≈ 180 GB。
  → 跑 GPU 实验前必须 ulimit -c 0。**2026-09-27 实际发生过**（203 GB）。

8. Do Not Repeat 清单（7 条，完整版见过程文档附录 G）

不要重复做的事：

1. 不要再怀疑是 FluidCKPT 导致 GLM-5.3 崩溃 —— 已用纯 SGLang 复现，与此无关
2. 不要再尝试翻 flag 绕过 NSA path —— 两条 HCU 分支共用同一函数，无解
3. 不要再把 NFS 当作权重分发通道 —— 比 NVMe 慢 9 倍、比跨节点聚合慢 760 倍
4. 不要再在 node28 上用 du -xsh / 判断盘满 —— overlay2 merged 挂载点对 -x 不可见，
   会严重低估（实测 80G vs df 的 414G）；要查就直接查 docker system df -v
5. 不要再排查 keep2 的"keeper 重启干扰" —— 机制上不成立，已定性为 ENOSPC
6. 不要再重搭 conda 环境 / 重装依赖 —— 环境是通的（sglang 环境已验证，pytest 可跑）
7. 不要再清理 node28 的 root 盘 —— 那是别人的镜像/容器（7 镜像 156 GB、17 容器 225 GB），
   不阻塞我们，未经许可不动
