## 17. 已明确的研究认识与未完成项

- 系统定位：拓扑感知的权重保活与快速物化；核心目标为权重开始加载到全部目标可用。
- 数学结构：预算约束副本放置＋多来源/多目标流量分配＋完成时间最小化。离散placement与连续flow联合，当前用MILP；固定布局恢复用LP。普通单商品最大流只覆盖简化子问题。
- 目标是max各rank完成时间，所以单独改善快卡可能没有总收益，成对决策可能有收益；不应机械均分字节。
- HBM恢复快但与推理争显存；本地DRAM省跨机但仍有H2D；远端HBM保留目标空间但仍搬运；多副本有选择性与容错价值，也会消耗容量。
- 当前没有证明“均分在任意硬件和目标下最优”；没有测每卡允许8 GiB后的集中vs分散；没有优化完整底本的迁移。
- 双缓冲为何未显著改善真实模型仍是开放问题；不能把event重叠当DMA并行，也不能从接收端RCCL驻留直接推出网络饱和。
- 本轮未实施多场景联合控制器、自动全模型候选生成、迁移峰值预算规划、在线反馈重规划。接口与阶段安排见新计划。
- 长期目标仍包括与SGLang自身保活进行严格对照，但当前结果不能宣称已经全面胜过所有SGLang保活机制。

## 附录 A：系统调用链、数据对象与加载边界

### A.1 为什么不能只记住“keeper保存权重、MILP选位置”

这句话遗漏了四件会直接影响正确性和计时的事情：

1. 保存的是处理后的TP shard，必须匹配模型、rank、张量布局；不是任意原始文件切片。
2. 规划所见候选、目录中的有效副本、推理进程中的目标storage，是不同对象。
3. 通信之前要让所有参与worker完成版本检查和目标准备，不能一边失败一边已经进入collective。
4. 数据搬完、发布可用、全量校验、释放租约是不同时间点；混成一个耗时会掩盖瓶颈。

### A.2 当前真实模型runner的调用链

```text
PlacementRun.run()                  # 继承SystemRun，宿主机协调
  isolated_containers()
  preflight()
  start_workers()
  fixture()                        # 本runner只记录本轮范围
  real_model()
    prepare_model()
      server(node27, capture)
      wait_exports(capture)
      worker.capture(...)          # 持有后处理后的rank快照
      generate(node27)             # 3个固定输入，参考答案
      verify_capture(...)         # 与当前推理模型逐字节核对

      migrate(model/base/* -> model/remote/* on node28 DRAM)

```

`fixture()`、四种路径校准、两次恢复不是同一类测量：前两者用于系统准备和模型输入；最终两次live恢复才是placement端到端对比。这里不存在五次重复真实模型恢复。

### A.4 五种对象及其生命周期

| 对象 | 创建位置/拥有者 | 关键字段或用途 | 不能混淆成什么 |
| --- | --- | --- | --- |
| 处理后快照Shard | Keeper capture/adopt | tensor、owner、meta、index、nbytes | 原始safetensors文件或Linux缓存页 |
| 实体Replica | worker Catalog.reserve/publish | id、identity、tp、off/n、tier、worker、epoch、generation、state、leases | 仅供求解的候选行 |
| 候选副本 | placement_case构造/求解器 | 可能的位置、区间、容量消耗与预测路径 | 已经分配并校验的可读来源 |
| Live HbmTarget | 推理进程导出，worker导入 | 元数据、IPC storage views、segs、starts | Keeper持久快照的别名 |
| Transfer transaction | coordinator与各worker | tx、plan、prepared targets、源leases、records | 已具备全局原子性的完整布局事务 |

“IPC导入是零拷贝映射”只说明跨进程共享目标storage的方式；快照到这些目标storage仍需H2D或D2D写入。因此不能由IPC机制推导“恢复全部零拷贝”。

### A.5 三种地址/偏移不能串用

- `op.off`：在整个rank逻辑快照中的起始字节。
- `op.source_offset`：在所选副本tensor内部的起始字节。
- `target.scatter()`内部偏移：逻辑区间与每个目标storage交集后得到的局部偏移。

目录检查要求`op.off = replica.off + op.source_offset`，且`source_offset+n ≤ replica.n`。新本地HBM副本从1 GiB+17开始；它的第一段source_offset应为0，而不是再次加1 GiB+17。附录H的实际op表保留这两个偏移，后续排查错字节时可直接核对。

### A.6 目标storage不是一个连续大tensor

`HbmTarget.__init__()`读取导出的meta和entries，用`torch.UntypedStorage._new_shared_cuda`建立视图；逐项核对model_identity、tp_size、tp_rank、tensors及名称/大小集合。

它将各storage组织成排序的`(offset, nbytes, uint8 cuda view)`，同时建立`starts`供二分定位。

当前scatter核心逻辑是：

```python
i = max(0, bisect.bisect_right(self.starts, off) - 1)
while i < len(self.segs) and self.segs[i][0] < end:
    o, n, t = self.segs[i]
    a, b = max(o, off), min(o + n, end)
    if a < b:
        t[a-o:b-o].copy_(src[a-off:b-off], non_blocking=True)
    i += 1
```

因此本次看到CPU侧scatter开销后，已经可以排除“代码每块都从第一个storage全表扫描”的具体猜测。不能由此排除所有Python提交开销：切片、多个copy调用和同步仍然存在。

## 附录 B：所有权、状态转换、执行器和错误处理

### B.1 NUMA DRAM分配的实际步骤

源码：`main_lib/fluidckpt/memory/host.py::HostAllocation`。

```text
校验backend/平台/显式NUMA节点
  -> 检查该NUMA的free+file-shmem估算及2GiB余量
  -> 页对齐的匿名mmap
  -> mbind(move=False)，新映射此时尚未触页
  -> torch.frombuffer建立uint8视图
  -> fill_(0)实际触页；此阶段暂将torch线程数设为1
  -> placement(samples=256)核对抽样页位置
  -> cudaHostRegister注册整个分配区域
  -> 保存owner/tensor和allocate_bind_touch/register分段
```

注意三层区别：申请逻辑字节数、页对齐分配字节数、底层分配器可能保留的物理空间不是同一个数字。普通`torch_pinned_default`后端不能仅由tensor长度得知allocator取整，代码将其allocation_bytes记为None。

256页位置抽样通过不等于逐页审计证明；触页与注册则是真实执行动作。路径不可用时明确抛错，不静默退回未绑定内存。

关闭时先同步GPU，注销host registration，再丢弃tensor视图并关闭mmap。这个顺序保护异步传输尚未使用完的页；NUMA目录的可用量估算也不等于已经实现全机多应用容量预约。

### B.2 为什么NUMA权限失败需要改实验容器而不是改测量结论

fixture02的失败链落在`ClusterWorker.allocate -> HostAllocation -> mbind`，不是LP求解，也不是内容不一致。

`run_system.py`在远端用已有镜像创建独立容器，加入SYS_NICE、memlock无限、core=0，映射GPU/IB设备、仓库以及只读模型路径。它没有把已有服务容器停掉，也没有用“mbind失败但继续运行”冒充NUMA可控。

后续每次preflight会重新检查NUMA能力、GPU占用和端口；历史一次成功不能代替新一轮的现场验证。

### B.3 Replica状态机和不变量

```text
reserve -> BUILDING -> 内容校验通过 -> publish -> VALID
                                                  |
                                                retire
                                                  v
                                              RETIRING
                                                  |
                                      leases==0 / release最后读者
                                                  v
                                               RELEASED
```

| 函数 | 实际检查/动作 | 保护的错误 |
| --- | --- | --- |
| reserve | id未被占用、tier合法、n为正整数、4KiB取整后容量足够 | 重复分配、容量透支 |
| publish | 必须BUILDING且verified=True | 把尚未填满或未校验的缓存当来源 |
| acquire | VALID、generation一致、identity/tp/worker一致、区间完全吻合 | 旧副本、错模型/错rank、越界 |
| release | 每个唯一副本lease减1，RETIRING且无人读取时关闭 | 提前回收和泄漏 |
| retire | 标RETIRING，有读者则延期 | 正在恢复时释放tensor |

`acquire()`先检查全部源操作，再统一给被选中的唯一副本加lease。同一副本被两个op读取不会按op重复加两次；中间一个op不合法也不会留下半批加过的lease。

同id释放后再reserve，generation递增。worker epoch包含session、节点/GPU、PID和UUID，不能把PID碰巧重用当成同一个worker。

### B.4 “不删最后完整来源”具体在哪里保证

`Cluster.retire()`先调用全局`check_retirement`：拒绝有读者的源，并检查移除它以后，同identity/tp的有效区间还能完整覆盖它的范围。

但底层`worker.retire`只管理本地目录和empty_cache，不独自知道所有节点的全局覆盖。实验驱动确有直接调用底层retire：它在明确保留完整node28底本的条件下删除额外缓存。

因此应写成“高层控制接口有全局覆盖检查，实验直接操作受底本前提保护”，不能写成“任何底层HTTP退休请求天然具有全局覆盖保证”。未来布局变更控制器应统一这些入口和前置校验。

### B.5 Transfer事务实际顺序

`Cluster.transfer()`先构造worker-specific envelopes，再把plan记入active；随后对所有worker并行prepare，等全部成功后才启动execute。

worker prepare会检查自身epoch、源epoch、全局目标覆盖和每个源lease，再按live/replica模式导入目标或分配目标。

这是避免collective故障的重要屏障：若某卡因容量或旧generation拒绝，其他卡尚未进入本次broadcast，可统一abort已准备的事务。

execute结束后，coordinator将目标角色的`op_id -> bytes`与plan逐项核对。这里只证明执行记录的范围一致；随后SHA256才检查内容。

```text
Replica构建：prepare -> execute -> 全量verify -> complete/publish -> finish
Live恢复： prepare -> execute -> complete/ready -> 生成检查 -> 全量verify -> finish
```

live分支允许先ready，是本实验为准确计量加载窗口采用的流程。不能声称weights_ready之前已经完成完整SHA256；若后续校验失败，实验整体应失败。

### B.6 全量校验和“全局原子事务”不能混称

`verify_run()`按op计算来源和目标SHA256。coordinator合并各worker返回值，检查同op元数据一致、没有缺op、n相符、source/target哈希一致。

代码会存`verified_rows`；`complete()`对新建实体副本要求该记录和verified标志。当前实现并没有每一步都进入一个独立的VERIFIED phase，不应根据允许的phase名称虚构状态转换。

所有worker的complete通过RPC分别执行。若某worker已将新副本发布为VALID，另一个complete失败，abort不会盲目删除已VALID的副本。所以现有transfer具备局部状态与清理保护，**不能被描述为完整布局跨节点全有或全无提交**。

`abort()`本身也可能遭遇GPU/远端进程故障；fixture04保留的abort连接错误正说明不能把“调用了abort”当成“所有远端一定清理成功”。当前runner记录cleanup_errors并回收自有进程/容器，未来控制层需要明确可恢复状态与重试规则。

### B.7 serial数据路径

每个worker按共同的ops顺序遍历，但跳过不属于自己的op。互不相交的pair可以独立推进。

```text
远端DRAM：注册CPU tensor -> 源GPU staging -> pair broadcast
          -> 目标GPU staging -> HbmTarget.scatter -> 设备同步

远端HBM：源HBM tensor -> 源GPU staging -> pair broadcast
         -> 目标GPU staging -> scatter -> 设备同步

同worker本地DRAM/HBM：直接取source view -> land/scatter -> 设备同步
```

每块最多32 MiB；最后一块保留准确n，不补成完整块。单缓冲只有在最后消费者完成后才能重用，因此serial在每块末尾调用设备同步。

“源worker的某op耗时”可能比同op目标耗时长：源先进入下一个broadcast时，目标还在处理其他来源。二者起点不一致，不能将二者差值简单解释为网络重传或某端内存更慢。

### B.8 double_buffer如何建立依赖

源码：`executor/pipeline.py::DoubleBufferCopier`。

| 角色 | 槽位k的顺序 |
| --- | --- |
| source | 等旧free[k]；copy stream拷贝；记录ready[k]；comm stream等ready；broadcast；记录free[k] |
| target | 等旧free[k]；comm stream接收；记录ready[k]；copy stream等ready；land；记录free[k] |
| both | 等旧free[k]；copy stream直接land；记录free[k] |

槽号为`chunks % 2`；重用槽前host等待该槽free事件，限制在途提交；每op结束drain copy/comm streams。异常路径同样尝试drain，再由上层abort处理。

`host_slot_wait_s`表示host等待槽可重用，不直接区分H2D、通信、对端等待或CPU调度。`trace_pipeline=True`的GPU事件区间也可能包含stream依赖，不能充当硬件引擎利用率证据。

## 附录 C：联合模型到可执行字节计划的逐层推导

### C.1 从副本边界切出逻辑region

固定布局恢复LP并不是给每个完整文件任意选一个来源。对每个target，它取目标起止与各有效副本的区间端点，形成互不重叠的region；每个region只保留完整覆盖它、且路径可执行的来源。

因此既可以表达完整底本＋局部加速副本，也不会从只覆盖前半段的副本读取后半段。模型/TP不同的副本在这个阶段已经过滤。

### C.2 当前path_for资源命名

| 条件 | 加入的资源约束 |
| --- | --- |
| 任意路径 | `in:<dst worker>` |
| 来源为DRAM | `dram:<src node>:<numa>` |
| 来源与目标不是同worker | `out:<src worker>` |
| 跨节点 | `net_out:<src node>`、`net_in:<dst node>` |
| 每条逻辑路径 | 额外path容量约束 |

kind区分`local_dram/local_hbm/peer/network`；`path_rates[kind+":"+source tier]`可覆盖通用kind速率。本轮因此能区分network:dram与network:hbm。

这是抽象共享资源模型，不是完整展开的PCIe交换芯片、内存控制器、网卡端口物理图。当前缺少直接观测的资源参数仍带近似；不能把节点net限额等同于已校准的网卡物理极限。

### C.3 固定布局LP的变量、单位与目标

对每个(region, source/path)建立非负流变量，加一个T。约束region总供给等于该region大小；每条path和共享资源的总流量不超过capacity×T；目标最小化T。

LP内部将字节换算为十进制MB：`n/1e6`，所以GB/s容量列乘1000。不能把这里的GB/s按GiB/s直接代入。

`serial_target_execution=True`再要求每个目标worker的`Σ(flow_MB/(rate_GBps*1000)) ≤ T`。这表达当前执行器各来源段顺序服务，不允许LP把所有段幻想成完全重叠。

### C.4 连续解如何变成整数字节操作

LP产生连续字节量后，`restore_plan`默认以4 MiB量化非主来源；将剩余精确字节交给该region分配量最大的来源。然后按连续cursor生成ops。

`validate_plan`检查每个target从begin开始无空洞、无重叠地覆盖到end，并检查tp、identity、目标worker与整数字节类型。

量化后的预测用实际ops重新计算，不能只报告未量化LP下界。代码分别保留`bandwidth_lower_bound_s`和`estimated_transfer_s`；本轮没有把两者混为数学上同一个对象。

### C.5 MILP在LP之上增加什么

`joint_placement()`把base与候选的边界一起切region。变量顺序为：

```text
[每个候选的binary x] + [每个region/来源的连续flow_GB] + [T]
```

不同于固定布局LP，MILP流量和容量使用十进制GB（`n/1e9`）。二元副本选择与其可供流量通过`flow ≤ region_size * x`相连；全局tier与每位置预算使用页对齐后的候选大小。

本次36个binary、52个连续flow、1个T，共89个变量。两rank各6个1 GiB块，每块三个位置选项，另外仍有完整底本可覆盖所有未缓存区域。

`scipy.optimize.milp`采用20秒time limit和1e-7相对gap设置。当前代码遇到非success就抛异常，**尚未实现超时可行incumbent的正常接管策略**；那是下一阶段接口改造项。

### C.6 返回的selected不等于已经存在的副本

求解后去除未实际供给流量的候选，再调用恢复LP验证所选布局的覆盖与量化后代价。这个验证是数学/计划层面的，不会分配物理显存或生成数据哈希。

实验候选由底本描述派生，可能携带源描述中的辅助字段；它们只是预测输入。真实执行必须通过runner重新构造target，并由目标worker reserve赋予正确的owner/epoch/generation，不能把候选的`state=VALID`当作实体目录发布证明。

这正是下一阶段需要独立Candidate、Replica、PlacementPlan契约的原因之一。

### C.7 为什么单副本贪心在本例选0

单副本贪心以当前T的下降作为收益，按收益/字节选下一项，仅接受大于1e-9的改善。

在本例底本方案中，两rank完成时间相同。只为rank0加一个本地副本，会降低rank0服务需求，但rank1仍保持原T；只为rank1增加亦然。因此每个单项的目标收益都是0，算法停止。

成对贪心将相同块位置类型的两个rank候选一起评估，能跨过这个平台；MILP直接联合选择，得到同样1.222444s的目标值。

这里证明的是当前构造下存在互补性，不是“所有贪心都无效”，也不是“MILP在任意规模都比贪心更快”。

### C.8 为什么最终执行balanced_local而不是原样执行MILP候选列表

`solve_placement_case.py`会依次比较balanced_local、paired_greedy、single_greedy是否在1e-6秒容差内达到MILP量化后的值；如果有，就选择这个简单等价方案，否则选择MILP。

本次balanced_local与MILP值相同。简单方案选择每rank前四个候选块做本地HBM，第五块做本地DRAM，之后由runner合并相邻区间。这样执行较易审阅，不必采用MILP在等价解之间任意选择的零散区间。

所以正确表述是“联合MILP提供模型内最优基准，实际执行达到同值的简单均衡布局”。不是“benchmark绕过了联合求解”，也不是“最终物理布局就是solver返回列表逐项不变”。

### D.2 rank0旧布局的四段来源

设G=1,073,741,824 bytes。以下半开区间用`[a,b)`表示。

| 区间 | 实际来源 | 字节数 |
| --- | --- | ---: |
| `[0, G+17)` | node28 DRAM model/remote/0 | 1,073,741,841 |
| `[G+17, 2G+17)` | node29 DRAM model/joint/0 | 1,073,741,824 |
| `[2G+17, 5G+17)` | node27 HBM model/gpu/0 | 3,221,225,472 |
| `[5G+17, 35,164,859,056)` | node28 DRAM model/remote/0 | 29,796,149,919 |

node27 HBM实体实际保存`[G+17,5G+17)`的4 GiB，但前1 GiB与本地DRAM重叠，恢复计划选择了本地DRAM，因此该HBM实体本次只贡献3 GiB。

rank1的逻辑区间一样，对应worker5/7/3及`*/1`副本。两个rank的数据内容并不因此相同，identity/tp和独立内容校验仍然必要。

### D.3 rank0新布局的四段来源

| 区间 | 实际来源 | 字节数 |
| --- | --- | ---: |
| `[0, G+17)` | node28 DRAM model/remote/0 | 1,073,741,841 |
| `[G+17, 5G+17)` | node29 HBM optimized/1 | 4,294,967,296 |
| `[5G+17, 6G+17)` | node29 DRAM optimized/0 | 1,073,741,824 |

rank1使用optimized/3 HBM和optimized/2 DRAM。17字节偏移不是单位换算误差，它保留了非整齐边界，能覆盖分段/尾字节正确性。

### D.4 三种“节约”必须分别计算

1. **物理缓存容量没有节约**：额外实体HBM和DRAM仍为8＋2 GiB。
2. **独立缓存覆盖增加**：旧两rank额外副本合计只覆盖8 GiB不同权重，新覆盖10 GiB。
3. **跨机字节减少8 GiB**：旧约63.5 GiB、新约55.5 GiB，准确差8,589,934,592 bytes。

源端DRAM供给的总逻辑量还会减少2 GiB：旧包含远端DRAM＋本地DRAM，新更多由本地HBM供给。但这些字节变化不能分别乘带宽后再与总加速叠加，因为路径共享资源、部分阶段并行，模型目标取最大完成时间。

### D.5 页取整与实际目录容量

每个完整底本逻辑35,164,859,056 bytes，Catalog记账为35,164,860,416 bytes，差1,360 bytes；两rank的完整底本目录记账合计70,329,720,832 bytes。

额外1 GiB/4 GiB块已页对齐，本轮两布局extra_tier_bytes相同。64 MiB/worker staging、RCCL上下文、推理模型自身空间并不包括在“额外8＋2 GiB副本预算”中；必须与副本容量分开报告，不能说全系统只占10 GiB。

retire时worker调用`torch.cuda.empty_cache()`，避免把目录tensor释放后仍留在allocator池中的显存误当作已归还物理空间。最终清理后各测试卡回到少量上下文/基线占用，node28其他业务不受影响。

### D.6 本次布局切换到底采用什么顺序

实验先完成原布局恢复与校验，保留node28完整底本，删除原额外HBM/DRAM副本，然后构建新额外副本。相邻同owner/tier区间合并后只有4个新实体：两份1 GiB DRAM、两份4 GiB HBM。

这保证了本例变更期间有完整底本兜底，也避免将旧10 GiB和新10 GiB长期同时保留。但它不是一般性的峰值预算最优调度器；对没有固定完整底本的情况还不能照搬。

18.880737秒建立成本包含4个transfer的分配、复制、协调和校验。没有与同口径“旧布局从相同起点建立”的成本形成严格配对，不能说这是新方案额外多花18.88秒，也不能据此计算精确回本次数。

## 附录 E：计时、收益归因与可排除的混淆

### E.1 为什么要保留三套时间

| 时间 | 起止/用途 | 不能替代 |
| --- | --- | --- |
| 目标加载窗口 | 同主机min(load_begin)到max(weights_ready) | 整个进程启动、HTTP服务就绪 |
| coordinator execute_wall | prepare全部完成后，到execute RPC全部返回 | 裸DMA时间或某一个目标的执行段 |
| worker op elapsed | 本worker进入某op到该op本地完成 | 纯网络带宽、跨机相同时刻区间 |

它们相互嵌套并含不同等待。per-op总和可以检查某worker内部账本，但不能把所有worker时间相加当作模型加载时间。

### E.2 主指标在源码中如何采样

`serving/measure.py`包装`ModelRunner.load_model`。进入前记录load_begin；原函数正常返回后同步GPU，再记录weights_ready；异常则记录load_failed。

`summarize()`要求每rank恰好一对合法begin/end，rank内所有事件和跨rank目标都属于同一host，拒绝跨主机monotonic相减。

这意味着“日志文件存在”不等于有效样本；重复边界、加载失败、跨主机混合会被明确拒绝。

### E.3 旧critical-rank分解并非算术错误，但不能直接作瓶颈归因

旧分析选择最后weights_ready的rank，沿该rank划分窗口，仍能严格相加到总时间。问题是：这张卡可能较早拷完，然后等待另一张卡，最后因通知顺序稍晚退出。

此时`copy_complete -> ready_publish`的大间隔里包含同伴搬运，不是独立控制工作。新分析选最后copy_complete的rank构造搬运主链，再把全卡拷完到最终ready作为尾部，减少误归因。

pipeline01最典型：旧“完成协调”0.257644秒，而两卡copy完成差0.248221秒；改用后一口径，全卡copy结束后的尾部约0.028267秒。

### E.4 0.320874秒总窗口改善如何对账

附录H.3逐项列出旧减新。主要观察是：

- 最后完成卡执行段缩短约105.954ms。
- 检测/规划/派发缩短约158.953ms。
- 映射缩短约116.040ms。
- 新样本入口/错峰增加约72.994ms，抵消部分收益。
- 其他layout/export/派发/收尾变化构成余项。

coordinator execute改善106.294ms，与目标执行段改善相近但并非完全相同，差异来自RPC和边界口径。不能再把两个改善相加。

### E.5 成本模型何处准确，何处偏乐观

旧布局预测1.358008s，对应execute实测1.361813s；新布局预测1.222444s，实测1.255519s。新方案预测相对实测偏低约2.6%（以实测为分母）。

局部例子更能说明边界：1 GiB连续目标本地HBM校准约2.895ms，线性外推4 GiB约11.58ms；真实模型worker6的4 GiB local_hbm op约36.06ms。

这个差额说明“连续小校准→真实scatter大操作”的线性外推尚未完全兑现，但不能只凭该差额断言CPU scatter是唯一原因：它也包含提交/同步、运行状态和测量波动。下一步应区分这些项，而不是把成本模型所有参数都整体调慢。

### E.6 不同实验之间不能横向拼排名

- control01的1.955185s属于控制面对照，不是placement01旧布局的配对样本。
- pipeline01的2.105821/2.090150s属于同布局执行器对照。
- profile01的2.439570s带采样，还可能包含首次通信准备，不能与普通运行直接算速度回退。
- bulk_profile01用连续目标且只有8 GiB/rank，不能替代65.5 GiB真实模型端到端。
- placement01只有两次配对布局样本，准备状态未完全对齐；它支持方向与当前观测，不能给稳定尾延迟结论。

这些限制不否定功能结果；它们规定的是可以从数据推到哪一层结论。

## 附录 F：Profiling排错链、工具语义与保留记录

### F.1 工具选择过程

本机检查发现rocprof/rocprofv3/perf未在所检查的PATH中，py-spy可用，DTK提供hipprof。先读本地hipprof帮助，再用独立`profile_smoke.py`验证动态采样。

smoke先做一次不采样H2D和同步，再调用roctracer_start，只采一次32 MiB H2D，再stop。生成的trace中存在一条HostToDevice GPU活动及对应HIP调用，说明工具能够看到实际设备拷贝，而不只是Python外层计时。

不要将“--help返回Invalid arg但打印Usage”误解为工具不可用；该版本帮助选项是`-h`。工具flag以本地版本为准。

### F.2 采样开关和采样范围

worker需设置`FLUIDCKPT_EXECUTE_PROFILE_DIR`，且计划含live target或显式`profile_execute=True`才进入ExecuteProfile。普通运行未设置该环境变量就走原执行路径。

hipprof以`--hip-trace --hiptx-trace --trace-args --trace-off --no-export`启动worker。应用内roctracer_start/stop把采样限制在execute，排除capture、构建和全量哈希。

ExecuteProfile还记录线程CPU、schedstat、上下文切换、每op起止，并用ROCTX标注op。结束后落cProfile和JSON。写报告和flush位于该wrapper退出阶段，也可能对coordinator返回时间产生干扰，所以诊断时间不当普通benchmark成绩。

### F.3 第一次GPU trace为什么不可用

原owned-process清理按进程组发SIGTERM，会同时结束worker和hipprof collector。应用内stop/flush并不等于collector已将SQLite事务提交完成。

会话中读原db曾遇到`database is locked`；拷贝未提交db并未得到完整活动表。原db与尝试的snapshot保留，没有通过“强行读取未完成文件”补造一个完整trace。

模型恢复、CPU profiling和GPU trace完整性是三个独立验收项：profile01前两项成功，后一项缺失。`device_trace_available=false`表示缺数据，分析器以None表示未知GPU活动/间隙，不以0冒充实测GPU空闲。

### F.4 正确收尾如何限制误杀

`stop_profile_worker.py`读取实验spec的pid/start_time，检查wrapper身份；再扫描同一process group中唯一的Python cluster.worker，重新核对其start_time。

只对这个worker发SIGTERM，让collector观察子进程结束并提交db；最多等待30秒，确认wrapper退出/变zombie，再由正常stop逻辑清理进程组。

`ProfileRun.stop()`使用finally调用原stop，避免诊断收尾失败后忘记owned-process清理。它不是按进程名全局pkill，也不会终止其他SGLang服务。

### F.5 第二次补测为何仍有failed状态

bulk_profile01的GPU trace完整，四个角色的拷贝字节总数匹配每rank 8,589,934,609 bytes，源/目标全量哈希一致。

但SystemRun在开始时记录`main_lib`和cluster脚本的SHA256；采样期间离线分析脚本被修改，结束时检测到唯一变化：

```text
AssertionError("measured code changed: ['codex_coding/src/task2/cluster/analyze_restore_profile.py']")
```

所以原始summary保持failed。分析器另给diagnostic_usable，依据是运行库/启动器未漂移、trace覆盖与内容检查通过。两种状态各自回答不同问题，不能合并成“全部passed”。

placement01在运行前完成所有已记录脚本的编辑，期间保持冻结，最终指纹和清理均通过。此次文档增强也不覆盖旧实验JSON。

### F.6 CPU与GPU记录分别能排除什么

主执行线程runqueue等待小，支持“本次采样未见该线程长时间抢不到CPU”；不等于系统所有CPU线程都无瓶颈。

cProfile中cuda synchronize self wall大，支持host在等设备依赖完成；不等于这些时间是CPU计算，也不直接说明等的是哪种设备资源。

GPU HIPCOPY提供实际copy活动及字节，可计算活动期间吞吐；RCCL kernel驻留可能含等对端供货，不能直接用模型字节除以它估算物理NIC吞吐。

### F.7 厂商D2H标签异常怎么核实

目标trace第一条被标为DeviceToHost的活动，source memory kind与destination memory kind都为Device；关联index对应hipMemcpyAsync(kind=3)。附录H.6保留原始字段。

分析器据双方Device将该活动归为D2D，并保留raw_names用于追溯。没有删掉这32 MiB，也没有为了让字节和对齐而修改原trace。后续换工具版本应重新确认，不把此修正推广到所有D2H记录。
