## 2. 从旧误差到新协议：因果问题与控制变量

### 2.1 为什么没有重测路径成本

旧simple r02的Hnear总高估284.765ms，其中搬运DAG高估约9.992ms、外层高估274.773ms；Hremote总高估396.767ms，其中DAG约7.472ms、外层389.295ms。外层分别解释带符号总偏差的96.49%/98.12%，因此本轮把“控制/物化/接管状态能否迁移”作为待验证问题。

`codex_coding/src/v0.1.23.3/task2/online_cost/review/outer_analysis.py:23`独立以路径表重算原worker依赖DAG；`:72`开始逐case读取旧raw和rank事件，`:100`构造7段同主机分区，`:113`核对分区和等于主指标。它没有把事后实测窗口送回预测器，也没有改旧模型。

旧C0的controller PID为7613，两个留出为9259；engine rank PID259/260、keeper PID46/47保持。恢复序号、布局、请求时段与controller进程同时变化。已有证据可以定位“旧统一外层残差迁移不良”，不能仅据此决定“全部来自首次调用”。Hnear后续请求的IPC映射仍比其他请求更慢，是必须保留的反证。

### 2.2 最小新设计及可回答的问题

| 设计动作 | 控制的变量 | 能检验的命题 | 仍然不能推出的命题 |

## 4. 数学模型与freeze的完整数据链

### 4.1 模型中真正变化的只有一个共同残差

记精确路径表为`s(path,n)`，原plan按extent及rank的op顺序记为`o_i`。原worker依赖DAG为每worker维护可用时刻`r_w`：每op开始于`max(r_src,r_dst)`，结束于该值加`s(path_i,n_i)`，再同时更新两端worker。`D(L)=max_w r_w`是布局L的搬运DAG预测。

独立实现见`codex_coding/src/v0.1.23.3/task2/online_cost/review/outer_analysis.py:23`；产品评分入口为`main_lib/fluidckpt/cluster/service_cost.py`的`estimate_execution()`，由`codex_coding/src/v0.1.23.3/task2/online_cost/model/predictor.py:149`调用。worker2同时参与两个目标的远端op，原DAG自然串行其服务；没有把两个remote rank当成可任意重叠的独立发送者。

本轮唯一拟合参数是`O = T(C0_cal) − D(C0_mixed)`，预测为`T_hat(L)=D(L)+O`，输出纳秒时才round。`model/predictor.py:198`要求O为有限且非负，负残差直接失败，不clamp、不事后修正。prime、旧C0、新旧holdout均不提供O。

数值为`O=2.903039095−2.4794586711796=0.4235804238204s`；旧simple外层为0.8080300058204s。12个路径服务点不变，候选共用同一个O，因此`T_hat(A)−T_hat(B)=D(A)−D(B)`；外层校准改善绝对时间及可行性判断，单凭O更新不能宣称solver改变候选排序或产生恢复加速。

## 5. 计时、verify、park与请求生命周期

### 5.1 主时间的代码边界

上述是本轮实际登记测量窗。未来论文比较完整请求入口或接入planner时，应重新核对每请求必要的准入、命令发布、inventory、规划及准备哪些属于主指标，并让所有对照采用同一边界；不能直接假定本轮覆盖全部入口成本，也不追溯修改本轮已冻结预测和误差。

### 5.2 ready之后仍要做完的正确性与物理暂停

`:231`先做ready资源门并保存，`:233`核sender原顺序；`:234`开始完整SHA、`:237`固定参考输出，要求检查70,329,718,112B且输出文本与bootstrap reference一致。`verify_before_ready=False`只是将全SHA移到主窗后，不能理解为跳过正确性。

### 5.3 7段分区和rank内部视图的关系

在同node27 monotonic时钟上，依次取controller begin、最早rank load、最晚rank load、最晚export、最晚map、最早execute、最晚copy complete、controller ready，得到7个连续分区。独审核这8个边界单调且7段之和精确重建T；其中rank arrival skew本身就是第二段，不应再次作为额外“外层项”相加。

每rank的load→layout_end、layout_end→export、accepted→mapped等窗口是另一种内部定位视图；两个rank可并行，且窗口已落在上述连续分区中。它们不能再与7段相加，也不能全部加总成唯一关键路径原因。worker执行时长、DAG及T的误差账同样是不同分解，后续章节分别列式和原始数值。

node30 sender串行仅在sender自己的clock domain内核op interval及顺序；不与node27绝对monotonic时间戳相减。跨run仅比较各自已经算出的持续时长。相同数字PID只在当前run/container/StartedAt/boot绑定范围内证明连续性，不表示跨历史容器复用旧进程。

### 5.4 四请求外面的bootstrap与最终cleanup

bootstrap另列模型加载、单映射capture、全量校验、固定参考生成、首次物理park、remote完整保活源和HBM cache准备。它不是本次恢复主时间，也不能从系统部署成本中消失；四请求中的prime仍完整计时，不与bootstrap混为一次免费预热。

### 6.1 三种不同时间量

### 11.2 决策前先回答的五个问题

1. 场景是否使预算、位置和共享资源同时影响选择，而非只有一条明显最快路径？
2. 同预算强简单策略与已有联合策略是否产生不同合法布局？同解则先报告同解，不自动增加求解器复杂度。

4. 对照是否获得相同的本地/远端/IPC/网卡候选机会？避免把额外NIC、额外副本或不同预算收益归因算法。
