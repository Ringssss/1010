## 0. 本文怎么用

本文的组织单位不是文件，而是 **patch（改造）**。每个 patch 回答四件事：

1. **插入点**：它切在 V0 工作流的哪一步。
2. **原状 → 改造**：动之前系统怎么做，动之后变成什么。
3. **为什么符合论文目的**：它兑现论文的哪一块，或明确标注"非论文"。
4. **状态与归口**：建到哪了、由哪个子任务驱动、证据在哪。

**改造类型**（决定它算不算贡献）：

| 类型 | 含义 | 论文含义 |
| --- | --- | --- |
| **新增** | V0 里根本没有这个能力 | 最可能是贡献点 |
| **替换** | 原来有，换成不同且更好的做法 | 可能是贡献点 |
| **增强** | 原来有，扩展了适用范围 | 通常不是独立贡献 |
| **复用** | 没动，只作依赖 | **列出是为了证明范围没蔓延** |

一个纯"复用"的模块如果出现在某轮建设清单里，要追问：为什么动它。

## 1. V0：我们所依赖的初版系统

### 1.1 V0 是谁

**SGLang 原生加载路径**，跑在多节点 GPU 集群上。

选它的理由：这是我们实际挂接的引擎——`serving/sglang_hook.py` 的两个 mode（`capture` / `restore`）就是插在 SGLang 的 `load_weights` 与 `process_weights_after_loading` 前后。证据链最完整，改造点最清楚。

Janus / BlitzScale / ServerlessLLM **不进主线**，只作为横向变体在需要对照时出现。否则 V0 会变成四系统对比图，看不清我们自己的演化。

### 1.2 V0 的架构（四层，比我们的能力栈少两层）

```
┌──────────────────────────────────────────────────────────┐
│ 引擎层   SGLang TP workers                                │
│    scheduler · KV cache · 权重常驻 HBM                     │
│    load_weights ← 从 safetensors 读分片                    │
│    process_weights_after_loading ← 格式变换                │
└───────────────────────▲──────────────────────────────────┘
                        │ 读文件
┌───────────────────────┴──────────────────────────────────┐
│ 存储层   本地 / 远端 SSD 上的 checkpoint 文件              │
└───────────────────────▲──────────────────────────────────┘
                        │
┌───────────────────────┴──────────────────────────────────┐
│ 集群层   多节点 GPU · IB / RCCL · NUMA 主机内存            │
└──────────────────────────────────────────────────────────┘

决策层   ✗ 不存在 —— 读哪个文件、从哪读，是写死的
证据层   ✗ 不存在 —— 只有端到端 wall clock
```

### 1.3 V0 的实际工作流（一次部署 → 一次退出）

```
① 调度器决定部署
      │
② 拉起 TP worker 进程（每 rank 一个）
      │
③ 每 rank 从磁盘读自己的 safetensors 分片
      │
④ process_weights_after_loading 做格式变换 → 权重进 HBM
      │
⑤ 进入 serving ………
      │
⑥ 缩容 → 进程退出 → 显存全部释放
      │
      └── 下次要用：从 ② 重来
```

### 1.4 V0 的三个"没有"——这是我们全部工作的起点

| 缺口 | V0 的实际后果 | 对应论文问题 |
| --- | --- | --- |
| **没有暂停态** | 只有"全留"（占着显存不放）或"全丢"（进程退出、重读磁盘）两种二元选择 | 论文中心问题的前提 |
| **没有跨位置** | 权重只在 HBM 或磁盘；NUMA DRAM、SSD 这类中间层不可用 | "放在哪里"无从谈起 |
| **没有决策** | 来源写死，不存在"选哪个来源、按什么顺序" | "联合决策"无从谈起 |

**关键推论**：论文的中心问题——"在受限且分布不均的保活预算下，联合决定存什么、放哪、怎么取"——在 V0 里**连提问的语法都不存在**。这不是"V0 做得不好"，而是 V0 没有这三个概念。所以下面的 patch 不是优化，是**逐步让问题成立**。

## 3. 各 Patch 详述

### P1 权重对象与暂停态

| 字段 | 内容 |
| --- | --- |
| **插入点** | V0 工作流 ⑤ 与 ⑥ 之间——把"进程退出"这一步切开 |
| **原状** | 权重与进程生命周期绑定。模型要释放只能退进程；退进程就什么都没了。系统里没有"这份权重现在在哪、谁持有、能不能安全释放"这类说法 |
| **改造** | 引入独立于进程的权重对象：identity（内容身份）/ epoch（incarnation）/ generation（版本）+ 覆盖证明 + lease。暂停 = 权重可被独立释放或保留，引擎继续存活 |
| **论文目的** | **这是"保活预算"约束得以存在的物理前提**。没有可独立释放、可迁移的权重对象，就不存在"存什么、放哪里"的问题——论文中心问题直接消失 |
| **类型 / 状态** | 新增 / ✅ 已建。实机：完整 Qwen TP2 70.33GB，全 SHA + 参考输出 + 物理 park（每 rank 释放 35.18GB） |
| **归口** | e1、e3、18.35 |
| **落地位置** | `cluster/catalog.py`、`serving/replicas.py`、`serving/lifecycle.py`、`serving/keeper.py`、`memory/owner.py` |

### P2 多层驻留

| 字段 | 内容 |
| --- | --- |
| **插入点** | V0 工作流 ③ 与 ④ 之间——权重进入 HBM 之前/之后，可在多层保留 |
| **原状** | 只有两个位置：HBM 或磁盘文件。中间的 NUMA DRAM、本地 SSD 层不存在，权重要么在显存里占着，要么回磁盘重读 |
| **改造** | 同一份权重可在 HBM / NUMA DRAM / SSD 独立保留与释放；每层有独立 owner 与容量账本；支持分片跨 NUMA 放置 |
| **论文目的** | 让"**放在哪里**"这个决策变量存在。没有多层，成本模型里就没有可选来源，规划器无事可做。这也是论文"分布不均的保活预算"中的"分布不均" |
| **类型 / 状态** | 新增 / ✅ 已建。实机：两节点三 GPU、两分片 DRAM 位于 NUMA4/7、SSD 层已接入 |
| **归口** | e2、e3、e6 |
| **落地位置** | `memory/{owner,numa,host,ssd}.py`、`serving/ssd_store.py`、`cluster/eviction.py` |

### P3 资源与路径真相

| 字段 | 内容 |
| --- | --- |
| **插入点** | V0 工作流 ② 之前——拉起进程前，先知道物理世界长什么样 |
| **原状** | 没有任何显式的物理资源模型。GPU 是几号、挂在哪个 NUMA、哪些路径能用、共享什么资源，全靠环境变量和约定 |
| **改造** | 有证据的资源地图：HIP 逻辑 ID ↔ PCI BDF ↔ DRM ↔ NUMA 完整对账；有向、会过期的路径证据；fail-closed 准入（证据不足就拒绝规划，不猜） |
| **论文目的** | 让"放哪里"**可计算**。没有物理真值，成本模型输入就是编的，规划器选出来的布局不可执行或不可信 |
| **类型 / 状态** | 新增 / ✅ 已建（有限域）。三节点六 GPU / 六 NUMA / 三 SSD 角色与必要路径已验证 |
| **归口** | 18.15、18.27、18.28 |
| **落地位置** | `topology/{discover,resource_map,placement}.py`、`cluster/path_catalog.py` |

### P4 成本模型

| 字段 | 内容 |
| --- | --- |
| **插入点** | V0 工作流 ② 之前——规划之前，先能估计"这个布局要多久" |
| **原状** | 没有成本模型。要么假设固定带宽，要么只有事后 wall clock。规划器即使存在也只能靠拍脑袋的速率 |
| **改造** | 状态条件的**精确服务点**：6 条路径 × 2 个实际尺寸，不拟合斜率、不插值、不外推；再加一次完整恢复的外层残差（控制 / 物化 / IPC / 接管）。明确标注"这不是裸带宽" |
| **论文目的** | 是"联合决策"的**依据**。没有可信成本，只能证明"在这个模型下更优"——模型本身错的话，这个结论一文不值。它是创新 ① 的必要条件，不是锦上添花 |
| **类型 / 状态** | 新增 / ✅ 有限域通过：同 controller 后续恢复 remote −0.187% / near −6.036%，两留出均过 10%，独审 73 项 |
| **归口** | e1、e4、18.35 |
| **落地位置** | `cluster/service_cost.py`（`fit_path` / `estimate_execution`）、`codex_coding/.../online_cost/model/predictor.py` |

> **注意**：`model/{resources,fluid,fit}.py` 下另有一套共享资源 max-min 公平模型，**属于更早的路线，不是当前主线**。当前主线是上面这套精确服务点。

### P5 联合规划器 ★论文创新本体

| 字段 | 内容 |
| --- | --- |
| **插入点** | V0 工作流 ③——决定"读什么、从哪读、什么顺序" |
| **原状** | 来源写死；或退化为逐块规则：每个块独立选当前最快的来源（就近 / fastest） |
| **改造** | 同预算下联合决定三件事：保留哪些块（存什么）、放哪个位置（放哪）、从哪些副本按什么顺序取（怎么取）。提供 nearest / fastest / balanced / resource LP / MILP / 多场景 MILP；并保留强简单对照（singleton/paired 边际贪心 + 交换局部搜索） |
| **论文目的** | **论文主张本体**。回答"联合考虑是否比强简单策略产生更好的决策" |
| **类型 / 状态** | 新增 / ⚠️ **已建但价值未证**。报告38 的符号实验里，"均衡＋交换"已追平 joint（5/6 vs 5/6），fastest 为 11/12。**加了 MILP ≠ 有贡献** |
| **归口** | e4、e5、18.36 |
| **落地位置** | `cluster/{planning,joint,multi_joint,control}.py`、`benchmarks/frozen_layout.py`（强简单对照） |

### P6 执行与引擎接管

| 字段 | 内容 |
| --- | --- |
| **插入点** | V0 工作流 ③–④——把计划变成真实搬运，并交给引擎 |
| **原状** | 只能走"读文件 → 进 HBM"这一条路。没有从别的位置取数、没有分块、没有跨节点搬运 |
| **改造** | 按计划执行 local / peer / network / SSD 搬运；有界 staging（64MiB）；逐路径字节精确流；HIP/RCCL 集合通信；IPC 接管——新引擎骨架直接绑定活进程已持有的权重，**不重跑加载** |
| **论文目的** | 让决策**能兑现成权重可用时延**。规划再好，执行不了就是空谈。这也是"规划收益能否兑现为主指标"的关口 |
| **类型 / 状态** | 新增 / ✅ 已建。实机：完整 Qwen TP2 恢复 + 全 SHA + 参考输出 + 引擎接管 |
| **归口** | e1、e3、18.35 |
| **落地位置** | `cluster/worker.py`、`executor/{chunks,regions,pipeline}.py`、`serving/{ipc_attach,layout,handoff,sglang_hook}.py`、`transport/` |

### P7 证据层

| 字段 | 内容 |
| --- | --- |
| **插入点** | 全程横切 |
| **原状** | 只有端到端 wall clock。不知道时间花在哪、不知道是否正确、不知道资源是否超 |
| **改造** | 计时合同（起止事件、时钟域、online/offline 边界）；正确性验证（全字节 SHA、固定参考输出）；资源账本（每层字节、预算、park 物理释放）；强对照与独立审计 |
| **论文目的** | 让结论**可信**。系统论文的每个性能主张都要能被独立复算；否则只是自说自话 |
| **类型 / 状态** | 新增 / ✅ 持续建设中。当前口径：主指标 = 完整 resume ACK 且全部 rank `weights_ready` |
| **归口** | 全程 |
| **落地位置** | `serving/measure.py`、`executor/profiling.py`、`codex_coding/.../task2/*/review/` |

## 4. 工作流演进：V0 → 现在

### V0
```
部署 → 拉起进程 → 读磁盘 → 格式变换 → 进 HBM → serving → 退进程 → 全丢
```

### 现在（一次暂停 → 恢复）
```
[离线] 部署 → 拉起 → 读磁盘 → 格式变换 → 进 HBM
                    │
                    ▼  P1 捕获 + P2 多层保留
              ┌─────────────┐
              │ HBM / DRAM / │  ← 保活布局建立（成本另列，不进主指标）
              │ SSD 多层副本 │
              └─────────────┘
                    │ 暂停（引擎存活，权重可释放）
                    ▼
[在线] 请求 → P3 读资源真相 → P4 估成本 → P5 选布局与来源
                    │
                    ▼  P6 按计划搬运 + IPC 接管
              全部 rank weights_ready  ←──────────────── P7 计时终点
                    │
                    ▼
              全 SHA + 参考输出 + 物理 park（P7，在主指标之外）
```

**边界要点**：P1 的捕获、P2 的保活布局建立、P3 的路径校准、P4 的外层校准，全部属于**离线**，成本另列。在线窗只含必要 inventory / plan / 物化接管 / 复制 / ACK。

> 2026-10-23 归档核验补充：`simple_controller.py:200` 附近的 park 证据、资源门、command 发布发生在 `begin` **之前**，不在已登记的 10% 资格窗内。接入规划器比较时，这些每请求必要前置项要统一审核归属，不能写成 0 成本。

## 7. V0 的三个"没有"现在还缺什么

回到第 1.4 节：

| V0 缺口 | 补上了吗 | 现在的实际状态 |
| --- | --- | --- |
| 没有暂停态 | ✅ 补上 | P1 已实机验证 |
| 没有跨位置 | ✅ 补上 | P2 已实机验证，多层可用 |
| 没有决策 | ⚠️ **能力有了，价值没证** | P5 已建；"有决策"≠"决策更好" |

**注意第三行**：这是整份文档最重要的一句。工程上我们已经从"写死的来源"走到了"可选的联合求解"，但**它是否真的比强简单策略选出更好的布局，至今没有证据**。报告38 的符号实验显示强交换已追平 joint；8GiB 真实实验里两者同布局。

### 一个尚待确认的结构性问题（2026-10-25）

按当前登记配置核算：每 rank 权重 32.75 GiB，per-card HBM 预算 48 GiB（物理 64 GiB），其中每卡 1 GiB 已被持久占用——**整个 rank 可以常驻，还余 14.25 GiB**。而路径服务点只按 (source tier, src→dst) 区分，不按 chunk 区分，所以同一层内放哪一块对总时间影响极小。

**18.36 阶段 1–2 已在 CPU 上证实。** 六策略在登记预算下选出相同布局、预测差为 0；扫到 8 GiB/card 仍同解；唯一分歧 `strong_simple` 差 5.7 ms（Δ 的 5.7%）。机制是 worker-clock DAG 的关键链：rank1 是关键链，比 rank0 慢 2.75 ms，移动非关键链上的 extent 在交叉前不改变 makespan。

**门 2 未过，整轮停止于 CPU。** 见[记录 51](experiments/2026-10-25_decision_value_cpu_gate2_result.md)。

需注意：压预算（方向 A）**已被证伪**——问题在于目标函数对 extent 可分离（单一 scenario + 同卡容量为唯一耦合），不只是预算宽松。

分离性已被测到精确形式：**分数是各 `(rank, tier)` 字节总量的纯函数**，同一总量下不同布局的分数偏差精确为 0（记录 51 第 6.1 节，`checks.py totals_only`）。这直接排除了一整类下一步设计：**任何"所有 extent 共享同一持有期"的线性保活代价，只是把两个总量重新定价，不会让"放哪一块"重新有意义**，与方向 A 同一个刀口。

因此四个候选方向的可执行性（记录 51 第 6.2 节）：

| 方向 | 状态 |
| --- | --- |
| A 压预算 | **已证伪** |
| B 分级保活成本 | 只有**依赖 extent 身份/时长**的形式可能有效；均匀时长的线性代价已被上式排除。但那需要"不同 extent 有不同价值/时长"的经验依据，否则是能调出任何结论的自由参数 |
| C 共享出口/多 NIC | **本项目的模型构建期就排除了它**：`simple_model.py:19-21` 硬性要求 `shared_resource_paths == {}`，登记模型该字段为空。→ 先补一次共享链路测量并重登记模型，才能谈 CPU 结论 |
| D 目标 worker 兼任 source | **登记候选集结构上不可能**：候选只放 `worker=rank` 自己的卡，`planning.py:40-41` 的 `"peer"` 分支永不激活。→ 先重登记候选域 |

另有一条独立于本结论的缺陷：`multi_joint` 的目标在"会用到 base 副本"的布局上比真实 makespan **低估约 47–49%**（源侧与目侧被当成互不相干的加和，而 DAG 里共享 worker 2 的 op 全部串行）。它只能当选解器，不能给这类布局排序。
