## 1. 目标、交付物与边界

### 1.1 核心目标

建立一个可重复、可替换算法、能解释性能变化的测试平台，使我们可以回答：

1. 权重实际保存在何处，位于哪个NUMA节点，消耗多少物理内存？
2. 每条可执行路径经过哪些硬件资源，单路与并发速度分别是多少？
3. 对给定的副本分布，哪种加载计划能让所有目标GPU尽早完成权重准备？
4. 更换存储、路径规划或复制算法后，收益来自哪里，是否正确、可重复？

主要指标是权重加载时间，不把Python进程启动、框架导入和HTTP服务初始化当成本任务的主优化方向。服务启动与真实生成仍用于验证恢复结果可用，并作为辅助指标保留。

### 1.2 分层交付

| 交付 | 内容 | 完成判据 |
| --- | --- | --- |
| D1：统一测量 | 所有算法共用加载边界、事件格式、结果分析 | 同一轮所有rank可对齐；异步复制与后处理完成才结束计时 |
| D2：资源地图 | GPU身份、NUMA、PCIe、存储和网络关系，附实测路径数据 | 身份无歧义；未知关系有标记；可追溯到原始发现与测量 |
| D3：主动DRAM保活 | 指定NUMA分配、物理页验证、显式生命周期 | 不依赖文件页缓存；保存和恢复均全量正确；实际容量有记录 |
| D4：算法测试接口 | 存储策略、规划器、执行器可独立切换 | 更换算法不需要改测试主流程 |
| D5：加载规划 | 就近、单路最快、共享资源规划的统一比较 | 计划合法、真实字节执行、预测误差可解释 |
| D6：扩展验证 | 从本机2卡扩展到更多卡、跨节点和多副本 | 前置阶段通过后逐级扩展，报告适用边界 |

功能完成与性能成功分开判断。平台可以正确完成但没有加速；不能将正确性通过写成性能目标达成。

### 2.3 必须保留的诊断结论

- 普通SGLang从node28的NFS路径加载原始文件；预热后可命中node27的Linux文件页缓存。Keeper恢复则从主动持有的、已处理的本机DRAM分片读取。
- `pin_memory=True`不保证NUMA位置。GPU编号、HIP逻辑编号、DRM card编号必须通过PCI BDF/设备标识对齐。
- 当前固定内存分配器按2的幂取整。小实验已验证32 MiB申请增加32 MiB物理内存，而32 MiB+1字节增加64 MiB；每rank约32.75 GiB对应64 GiB分配档的解释与大模型PSS吻合。
- 恢复`flow_s`包含映射、缓冲准备、复制和同步，不能直接当作纯PCIe带宽。
- IPC导出的引用不能反复当成全新句柄导入。继续复用已修复的单次导入、验证租约和显式释放机制。
- 已有资源模型在部分跨NUMA并发组合中失效。未知竞争模式不得通过理想带宽相加进入“最优”计划。

## 3. 从Helix借鉴的方法与必要改动

| Helix方法 | 本项目采用方式 | 不直接照搬的内容 |
| --- | --- | --- |
| 测量计算与网络能力后统一为token/s | 路径统一为bytes/s，容量统一为bytes | 推理吞吐不是加载完成时间 |
| 联合优化层放置和请求路径 | 先固定副本做恢复规划，再优化副本放置 | 权重分片具有身份，不能作为可互换的单商品流 |
| 节点拆为入口、出口以约束容量 | 显式表示GPU入口、网卡、NUMA读写等共享资源 | 无法忠实表示为单边的竞争继续使用额外约束 |
| MILP选择离散放置，最大流评价 | 固定布局先用LP，必要时用小规模组合枚举/MILP选择副本或路径 | 不用分数副本取整后直接宣布合法 |
| 按流量比例执行请求调度 | 按字节区间、并发窗口和限速执行计划 | 不按大小不同的块的个数盲目轮询 |
| KV-cache高水位限制 | 对实际DRAM分配、HBM暂存、在途块进行容量检查 | 权重大小已知，应做精确预算 |
| 分离放置与调度消融 | 分离NUMA放置、复制实现、路径规划、副本策略 | 不将多处同时修改的收益归给一个算法 |

## 4. 测量契约：只围绕权重加载公平比较

### 4.1 时间边界

定义`load_begin`为：运行环境已具备执行加载的条件，rank进入统一权重准备入口，尚未执行本次加载专有的模型分配、句柄导出/映射、动态规划或复制。

定义`weights_ready`为：该rank的所有必需参数、buffer、派生属性已经有效，必要的布局/后处理完成，所有写入目标权重的GPU操作已同步完成，可以交给推理引擎使用。

- 新指标：`T_load = max(t_weights_ready[rank]) - min(t_load_begin[rank])`。
- 保留每rank耗时和入口到达偏差，揭示慢rank和启动偏斜。
- 不以`flow`返回、HTTP监听或一句`fired up`替代`weights_ready`。
- 不把映射和临时缓冲分配提前到计时外，再与包含这些工作的算法比较。
- 如另设“已预建目标缓冲”的实验，明确其起始状态和预建成本，所有候选算法使用相同条件。

在单机上记录`monotonic_ns`，进程间共用同一主机时钟域。跨机器的单调时钟不能直接相减：使用协调器的开始/完成消息窗口作为集群指标，同时记录各rank本地时长、消息延迟与时钟误差；未经校准不拼接不同主机绝对时间。

如使用计时前barrier使所有rank就位，应对所有算法相同，并单独记录barrier等待。报告自然启动到达偏斜与受控加载时间两个量，不能悄悄删除慢rank等待。

### 4.2 分段事件

| 事件/耗时 | 范围 | 记录方法 |
| --- | --- | --- |
| `model_layout` | 空模型、目标storage、必要布局构建 | CPU单调时钟；注明异步GPU工作归属 |
| `source_prepare` | 文件打开/解析或副本定位、manifest验证 | 单调时钟、文件与缓存状态 |
| `plan` | 本次需求专有的规划时间 | 单调时钟；缓存计划记录命中与生成成本 |
| `target_map` | 导出、导入、IPC映射与目标校验 | 按rank及storage计数记录 |
| `buffer_prepare` | 分配、注册和触页等 | 主机时钟、实际分配字节、NUMA分布 |
| `transfer` | H2D、D2D/P2P、网络或SSD数据操作 | bytes、CPU包围时间、适用时用GPU events |
| `finalize` | 数据相关后处理、依赖等待和最终同步 | 单调时钟、依赖事件 |
| `weights_ready` | 可用边界 | 全部依赖完成后发出 |
| `verify` | 全量字节/数值和推理验证 | 单独计时，不加入性能主指标 |

存在流水重叠时，不能把所有事件时长机械相加；保存区间、stream与依赖关系，报告关键路径和阶段重叠。普通加载器的分段探针先覆盖真实执行分支，不强行套用恢复器事件。

### 4.3 一次性成本与辅助指标

- `T_capture`：保存、内存分配/注册、D2H及manifest生成。
- `T_replica_build`：额外副本建立时间、搬运字节和内存成本。
- `T_setup`：Keeper启动、通道准备、离线建模与离线规划。
- `T_service_ready`与固定请求延迟：只作辅助指标和正确性验证。
- `T_release`及显存/PSS变化：验证真正释放资源。
- 复用N次时报告`T_capture + T_replica_build + sum(T_load)`，与同样N次基线比较；避免只报告恢复收益、不报告预先付出的成本。

### 4.4 实验公平性

- 固定模型内容指纹、TP大小、dtype、版本、GPU集合、后端、核序列化设置、分块和缓存条件。
- 当前`AMD_SERIALIZE_KERNEL=3`保留为初始基线条件；若后续改变，所有算法一起重建基线，不与旧结果混算。
- 文件缓存分为“观测到的未充分缓存”“显式预热并验证”“受控冷读”。首次运行不能自动命名为冷读。
- 每轮记录文件页驻留比例、挂载方式、文件路径、实际读取计数（可获得时）、NUMA空闲与可用内存、GPU占用。
- 不在共享主机执行全局`drop_caches`。如需受控冷读，使用隔离的专用测试条件或明确标识的直接I/O微基准；后者不能冒充原生SGLang加载。
- 单次排障用于定位，不进入最终性能统计。阶段方案稳定后，至少5个完整独立加载样本，报告中位数、最小/最大值和每次原始值；5次样本不宣传稳定p99。
- 算法顺序交替或随机化，固定预热策略，避免运行顺序决定胜负。独立进程与常驻Keeper的状态分别声明。
- 正确性失败的样本必须保留并计入失败率，不能作为“异常值”删除。

## 5. 硬件与访存拓扑

### 5.1 三张表

**设备身份表**记录：节点ID、GPU稳定标识/PCI BDF、容器内可见序号、HIP序号、DRM映射、NUMA亲和、PCIe祖先链、网卡与SSD位置、NUMA容量和距离。属性包含发现来源、时间和环境指纹。

**路径能力表**记录：源/目标位置、方向、传输实现、块大小、单路带宽、固定开销、线程与内存绑定、依赖资源、并发适用范围、样本数和分散程度。

**副本目录**记录：模型版本、TP配置、rank、storage/字节区间、dtype/shape/stride/offset与别名关系、manifest版本、所在节点/NUMA/GPU、实际分配字节、有效状态和租约。

### 5.2 探测顺序

1. 主机与容器分别枚举设备，通过BDF/稳定设备标识连接逻辑编号。
2. 获取CPU socket、NUMA节点与距离；将“NUMA节点”与“整颗CPU”区分。
3. 获取GPU、网卡、SSD的PCIe路径；缺失或冲突信息标记为未知，不补猜测值。
4. 对候选NUMA内存分配后查询页面落点，验证绑定生效。
5. 对GPU近端与远端NUMA做少量定向传输，核对硬件报告与性能现象。
6. 固定拓扑快照。设备可见性、容器配置或拓扑变化时使相关测量失效。

物理连接不直接等价于可叠加带宽。共享瓶颈以竞争实验验证，不仅凭PCIe树推断。

## 6. 主动NUMA内存与副本生命周期

### 6.1 内存后端

保留`torch_pinned_default`作为对照，新增`numa_registered`后端：匿名mmap → 指定NUMA策略 → 触页 → 查询落点 → HIP host register → 暴露字节缓冲。

- 将现有`HostBuffer`能力整理到`main_lib/fluidckpt/memory/`（拟新增），供Keeper和Profiler共同使用；避免产品代码依赖一次性实验脚本。
- 除页/注册对齐外，避免按2的幂扩大整个rank缓冲。实际保留量仍通过PSS、映射和后端信息确认。
- 保存明确的owner对象和tensor/view引用，禁止只保留裸指针导致底层映射提前释放。
- GPU固定内存注册的返回码和NUMA绑定错误必须抛出。权限、容量不足或不支持时不能静默退化成“已绑定”。
- 释放顺序：停止新任务 → 等待相关DMA完成 → 释放IPC与tensor/view → 注销固定内存 → 解除映射。
- 记录实际页面分布，目标节点之外的页必须解释或判失败。抽样覆盖首尾、块边界和均匀分布，注明抽样不能证明每一页；条件允许时增加全页统计。
- 对大分配设容量预检与回滚，评估实际可回收内存，不把`free`字段当作唯一可用容量；不自动挤占其他用户的固定内存。

### 6.2 副本状态

```text
ALLOCATING → CAPTURING → VALID → RESTORING → VALID
     │            │                  │
     └────────────┴────→ FAILED ←─────┘
VALID → RELEASING → RELEASED
```

只有`VALID`副本可作为新计划的数据源。状态与版本原子发布；保存失败不发布半份副本；同一副本恢复期间需要读租约，不能被释放。失败后是否仍有完整源副本由明确状态判断。

## 7. 算法与数据接口设计

以下为拟新增契约，不要求沿用所有名称，但语义必须保留。

| 接口 | 输入 | 输出/职责 |
| --- | --- | --- |
| `TopologyProvider.discover()` | 节点/设备选择 | 带来源和版本的`TopologySnapshot` |
| `MemoryBackend.allocate()` | bytes、NUMA、注册选项 | 有owner、placement、实际容量、close的缓冲对象 |
| `ReplicaStore.capture()` | 导出manifest、放置策略 | 完整、版本化的`ReplicaManifest` |

| `Verifier.verify()` | 源身份、目标身份、验证策略 | 全量一致性、结构一致性、推理对照结果 |

### 7.1 最小统一配置

所有实验通过配置选择`memory_backend`、`placement_policy`、`planner`、`executor`，不在主流程中写死算法分支。配置还包含模型/设备、TP、缓存策略、块大小、并发数、重复次数和profiling版本。

第一版算法集合：

- 存储：默认固定内存、NUMA绑定注册内存。
- 放置：已知近端、指定远端（诊断）、显式候选布局。
- 规划：固定本地、就近合法来源、单路最快、资源贪心、资源约束LP。
- 执行：当前中转缓冲实现；直接H2D到目标storage作为独立候选，需实测而非预设更快。

### 7.2 计划合法性

执行前必须验证：每个目标区间完整覆盖且不重叠；源确实持有该区间；model/rank/TP/layout匹配；尾块没有漏字节；缓冲容量足够；依赖无环；所有操作为当前执行器支持的能力。

HIP IPC只表示同机进程间显存访问，不是跨节点句柄。当前Keeper不能直接访问另一个进程私有DRAM；跨Keeper本机来源必须先实现显式共享映射或所有者执行传输，未实现前不进入合法路径集合。

跨节点仍按当前环境已验证的集合通信能力执行，不能将不工作的send/recv当作候选。所有参与rank的collective顺序必须一致。

### 7.3 结果格式

每次运行生成独立目录，至少包含：配置及指纹、拓扑快照、缓存/资源快照、manifest摘要、规划结果、逐rank事件、执行字节、正确性结果、退出和资源回收情况。原始结果放`codex_coding/results/task2/`，不写入`docx/`。

失败结果写明stage、rank、操作、预期/实际值。保持旧结果只读，新算法不覆盖旧实验。

## 8. 路径规划方法

### 8.1 固定布局下的连续分配

设分片i需要`D_i`字节，合法路径集合为`P_i`；`x_ip`为经路径p搬运的字节量；路径上限为`B_p`；共享资源容量为`C_r`；`a_rip`表示该传输消耗资源r的系数。

```text
minimize T
subject to:
  sum(p in P_i) x_ip = D_i                  for every demand i
  sum(i) x_ip <= B_p * T                    for every path p
  sum(i,p) a_rip * x_ip <= C_r * T           for every resource r
  x_ip >= 0
```

容量与时间使用一致单位。目标GPU已拥有有效数据的区间无需搬运，但其验证和映射成本仍按相应实验模式计入。

该模型是忽略部分固定开销的连续资源分配模型，其最优值只能作为相应假设下的参考下界；不宣称真实系统全局最优。多rank需求保留独立身份，不能用最大总字节流量替代所有需求完成。

### 8.2 固定开销与可执行性

- 单路建模先使用`alpha + bytes/beta`，分别标记映射、分配、调用等固定成本。
- 初期枚举少量合法路径组合，再对组合内的字节分配求LP。共享初始化不重复加到每条路径；存在重叠时按依赖图计算完成时间。
- 对小流量路径检查收益是否覆盖准备开销；剪枝后重新求解并确认每个需求仍可达。
- 字节量取整到执行粒度后，重新校验覆盖和容量，重新预测完成时间。不能继续引用取整前的精确最优值作为实际计划耗时。
- 实时规划耗时计入加载；离线通用规划成本单列，计划过期或布局变化必须重新计算。
- 求解设置预算并始终保留就近合法路径方案。只在模型覆盖范围内采用预测优化，超出范围先补测或回退。

### 8.3 放置优化与运行时调度

在固定布局恢复通过后，再加入“是否建立副本”“启用哪些位置”的离散决策，容量预算使用实际分配字节。先小规模枚举，再按需要扩展MILP。

执行器将流量比例落到真实块的交错提交、在途窗口和限速上；反馈每个资源的完成速率与排队，避免名义上并行、实际串行。若资源容量变化，优先在块边界暂停/重排，禁止对同一区间重复并发写入。

## 9. 分阶段实施与验收

下表阈值是本计划提出的工程门槛，不是已有实验结论。阈值如需调整，应依据数据解释原因。

### P0：统一计时与基线

- 实现统一加载事件，普通加载与恢复共用边界；确认普通加载器的真实分支。
- 将GPU选择、rank数、重复数与算法参数从`run_loop.py`提取为配置。
- 记录当前环境与原始基线，保留既有`loop03`不变。
- 验收：无缺失rank；所有GPU写入在结束事件前同步；能解释阶段重叠；准备成本无隐藏。以至少5次普通加载和当前恢复形成新口径基线。

### P1：拓扑身份与放置观测

- 自动发现node27设备映射、NUMA和PCIe关系；对前期手写GPU→NUMA映射逐项核对。
- 新增匿名内存绑定、页面查询的小测试；检查分配失败、权限限制和容量不足路径。
- 验收：所选2张卡身份可唯一映射；绑定与查询结果一致；未知位置不能被规划器当成已知近端。

### P2：将NUMA内存接入Keeper

- 整理内存owner抽象，实现默认与NUMA注册两种后端。
- 先小张量、非对齐尾部、共享storage/别名测试，再全量Qwen分片。
- 执行保存 → 释放原服务 → 恢复，保持复制和规划实现不变。
- 验收：全量字节零差异；位置检查通过；显存回收；注销和mmap生命周期无泄漏；大模型重复5次无功能失败。
- 内存目标：明确消除现有每rank32.75 GiB向64 GiB取整的主体浪费；报告实际保留量、PSS与逻辑字节之差，不把进程共享页重复计数。

### P3：校准路径与竞争模型

- 分别测近端/远端DRAM→GPU、D2H和候选P2P；针对2张卡测并发本地、共用NUMA、跨NUMA及双向竞争。
- 块大小初始取4、16、64、256 MiB、1 GiB；先用小分配验证，再在容量允许时增加工作集。
- 分开预热与测量；除重复小缓冲，还测轮转大工作集或真实分片，避免把缓存友好微基准当成模型恢复能力。
- NUMA、分配器、块大小、GPU序列化设置一次只改变一个因素。
- 数据划分为拟合与保留验证集，验证集不回灌拟合后继续自称独立验证。
- 验收：每条启用路径有实测记录和适用范围；无占位容量进入优化；目标保留集完成时间预测误差中位数≤10%，超过20%的场景逐项解释或排除。

### P4：建立可替换算法的稳定测试入口

- 接入第7节契约，配置化算法选择，自动输出逐次结果和汇总表。
- 确认换存储后端不换复制算法，换规划器不换布局和执行器。
- 增加故障验证：错模型/错rank、缺块、失效副本、无效句柄、复制异常、超时和容量不足。
- 验收：每类错误停止本轮，不能发出成功完成标记；异常只清理本轮资源；完整结果可由配置和版本复现。

### P5：接入规划与真实字节执行

- 统一现有单机/跨节点规划数据结构，第一版启用单机受测路径子集。
- 对手算小例子验证共享瓶颈、独立通路、单一来源、不可达、尾块取整。
- 固定副本布局，比较就近、单路最快、资源贪心、LP。
- 确认有多个真实合法来源时才开展多路径性能比较；单来源场景允许规划器退化为同一路径。
- 验收：执行字节覆盖精确、全量数据正确；预测与实际差异有分段证据；规划耗时、额外缓冲与源准备成本均报告。

### P6：消融、重复性与性能结论

- 按第10节实验矩阵逐组比较，先同机2卡，再按资源情况扩展。
- 先5次取得稳定性判断；主结论候选做至少10组交替/配对测量，并对配对差异计算置信区间或明确显示波动。
- 稳定性目标：固定环境下加载时间`IQR/median≤10%`。超出时先排查资源竞争、页面位置、首次映射与缓存状态。
- 性能目标：相对同条件最佳有效基线，中位加载耗时减少至少10%且配对结果支持正收益，才标记“达到第一阶段加速目标”；未达到则如实报告功能完成及瓶颈。
- 避免只有对NFS首次慢加载的巨大倍数；同时报告预热文件加载、默认DRAM恢复和NUMA恢复。

### P7：多卡、多节点与副本放置扩展

- 2卡通过后扩展到4/8卡，重新测NUMA/入口/内存带宽竞争，不将单卡带宽直接相加。
- 跨节点先两机，后加入第三个副本节点；每台机器独立发现拓扑和带宽。
- 新增跨节点副本复制、collective顺序和通信失败测试。只有真实全量数据验证通过后才比较规划收益。
- 增加容量受限、多副本、源节点竞争场景；固定布局优化通过后再开启布局搜索。
- SGLang自身保活基线作为独立比较项：先核实依赖和支持范围，确保相同源数据状态与资源释放要求；无法运行时标记缺失，不用冷启动替代。
- 验收：逐级形成独立结论；单机通过不能自动推导跨节点或其他模型通过。

| ID | 设计动机 | 控制变量/操作 | 预期与判据 |
| --- | --- | --- | --- |
| E01 | 确认设备身份 | 主机、容器、HIP映射对齐 | BDF/稳定标识一致，发现冲突立即停止路径构建 |

## 12. 阶段门槛、回退与资源清理

| 发现的问题 | 处理方式 |
| --- | --- |
| GPU身份或NUMA信息冲突 | 回到P1，以BDF和实测核对；不生成依赖猜测的计划 |
| 内存绑定/注册失败或容量不足 | 显式失败、释放本轮分配；不默默跨NUMA分配 |
| 数据、shape、stride、别名或派生属性不一致 | 停止性能比较，按最小复现定位第一个不同区间 |
| 复制线程或通信失败 | 错误传回协调器；不生成ready/done成功事件 |
| 测量波动过大 | 核对页面放置、系统负载、缓存、映射冷暖和序列化选项，再做定向实验 |
| 模型预测偏差超过门槛 | 分离单路能力和共享竞争，限制可用路径或回退就近方案 |
| 规划器超时/无可行解 | 返回已验证合法基线；无有效副本则明确不可恢复 |
| 资源或版本变化 | 失效相关拓扑/性能快照与计划，重新发现或补测 |

清理只针对本轮创建的进程组、句柄、缓冲和临时文件。禁止用宽泛pkill清理其他实验；不复用旧`done`标记；每个run使用独立handoff目录。清理后验证显存与Keeper内存回收情况，保留失败日志。

本计划不新增审批门槛：进入已授权的执行范围后，按阶段验收自动推进可逆开发、检查和实验；阶段失败先自主诊断。任务范围发生实质变化或缺少必要信息时，再与用户讨论。
