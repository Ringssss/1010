## 1. 目标与建设层次

从“实验脚本中解一次固定placement题”推进到可复用的联合规划控制层：给定模型、资源预算和恢复需求，输出可解释、能执行、可验证的保活及恢复方案。

主指标保持权重开始加载到全部目标可用。当前单模型Qwen TP2是第一验收载体。暂不将TP重分片、KV会话恢复、训练状态或生产级分布式一致性混入本阶段。

现有基础：NUMA显式分配与GPU注册、版本化副本目录、事务执行、resource_lp、单场景有限候选MILP、真实生成与全量字节校验。

缺口：候选和预算人工生成；joint未接成统一placement接口；切换步骤在实验脚本中；成本模型只做过局部校准；多恢复场景和自适应反馈尚未闭环。

## 2. 输入、输出与责任边界

### 输入

| 对象（拟建名称） | 必须包含 |
| --- | --- |
| ResourceSnapshot | worker/session/epoch，节点/NUMA/GPU/NIC及共享资源关系，容量、已占用、应用预留、采集时间与版本 |
| RestoreDemand | 模型identity与TP布局、目标rank到GPU映射、恢复场景、重要程度/频率、并发还是互斥场景 |
| PlacementBudget | DRAM/HBM分层预算、物理位置预算、推理预留、通信缓冲、临时迁移空间、底本/覆盖策略 |
| CostProfile | 路径、来源层、字节规模、并发组合、执行器、有效服务率/准备项、样本来源与版本 |

### 输出

| 对象（拟建名称） | 必须包含 |
| --- | --- |
| PlacementPlan | 候选定义、选择的副本、场景成本、容量账本、求解状态/界限/gap、预计收益、依赖快照版本 |
| TransitionPlan | 新增/迁移/保留/释放动作，执行依赖、临时峰值占用、任一步的覆盖保证、失败处理 |

## 3. 阶段一：统一资源与需求接口

**目的**：每份计划的输入明确、可复查，避免人工散落的4 GiB上限被误当作物理定律。

**做法**：复用探针和inventory；统一逻辑GPU、BDF与NUMA标识；把副本容量、推理预留、缓冲和迁移临时量区分记账。以物理NUMA/设备作为共享容量归属，不能让两个worker各自宣称拥有同一份物理内存预算。

首版恢复需求由明确配置提供，不需要先建设复杂的需求预测器。恢复目标变化与同时多请求竞争分别表达。

**交付/验收**：可序列化输入契约、schema/版本校验、资源不可用和预算不合法的可解释拒绝；重复快照不应重复计算同一分配。

## 4. 阶段二：自动生成候选

**目的**：从完整权重清单生成合法选择空间，比较集中、不均衡、均衡、多来源方案。

**做法**：先用约1 GiB粗粒度规划块限制规模，尾部保持精确字节覆盖；执行分块仍可为32 MiB。候选覆盖全部需要的权重，而不只手选前几GiB。按可达性、容量、推理预留、identity与固定TP过滤；过滤理由写入报告。

每卡上限来自预算输入；设计一组真的允许单卡8 GiB的场景，与4+4和其他分配比较。目标侧不足时允许远端候选。完整底本是否固定为显式策略开关，不能悄悄删除保障。

**交付/验收**：候选生成器、无遗漏覆盖、尾字节/页取整测试、候选裁剪审计。候选数量增长后先记录规模与时间，不沿用“小模型MILP只需8.7ms”的保证。

## 5. 阶段三：执行器一致的成本模型

**目的**：预测排序要与实际实现相符，避免在数学中假定不存在的重叠。

**做法**：区分来源层、NUMA、目标GPU、大小和并发组合；保留资源容量约束，另按serial或double_buffer描述可实现的依赖与重叠。标称400 Gb/s、HIP kernel驻留时间、单路有效路径速率不能互换。

准备/注册/映射/首次调用成本单列；当前先预测传输，完整加载由明确分段组成，不把CPU协调区间与GPU活动时间再次相加。CostProfile附样本和有效范围，未知组合标记为未验证。

**交付/验收**：统一评分接口、预测误差报告；先验证可解释的方案排序，不硬性要求每个样本都快或每次误差极小。校准通常一次，明显异常才补第二次。

## 6. 阶段四：联合求解接口

**目的**：让当前`joint_placement`成为正常控制流程可调用的能力。

**做法**：先单目标，离散副本变量与连续恢复flow变量联合；约束空间、完整来源、共享带宽、目标完成时间。再加入多个互斥未来场景，使用共享placement变量和各场景flow；可配置平均或最坏场景目标。

并发恢复不能只做概率加权，应在同一次共享资源模型中合计需求，后续单独扩展。

求解器应输出可行性、超时、incumbent、最优界限和gap；仅在确有证明时称模型内最优。超时但有可行解时先验证再用；不可行/错误时保留现有合法布局，记录回退，不能静默变成nearest后仍标最优。

**交付/验收**：统一plan接口及小规模穷举对照；对称、非对称、零预算、集中候选、目标变化测试。恢复阶段继续明确记录requested/actual策略。

## 7. 阶段五：布局变更执行器

**目的**：解决“终态放得下，中间却爆内存”以及迁移中丢失唯一副本的问题。

**做法**：对比新旧目录，生成依赖有序动作。复用BUILDING/VALID/RETIRING/RELEASED、generation、epoch和leases；新副本校验后发布，再决定旧副本退休。已有读者的副本不能强行释放。

允许两种预算可行方式：有临时空间时先建后撤；无临时空间时，先释放被完整底本保护的冗余副本，再分批建设。不能机械要求“所有新副本先建完”，也不能为回滚承诺超出实际空间的完整旧布局常驻。

失败时必须维持可恢复覆盖、清理未发布目标，报告当前实际目录；重试需可识别已完成动作。源或worker版本变化时重新检查/规划。第一版保持单coordinator，不额外扩成分布式共识工程。

**交付/验收**：TransitionPlan、分步容量/覆盖检查、变更中途失败和重试、预算紧张时可执行顺序、lease冲突保护。

## 8. 阶段六：恢复请求衔接

**目的**：把较重的保活决策移到恢复关键路径之外，恢复时按真实状态快速分流。

保活规划在模型进入保活、预算/需求明显变化时运行；恢复LP在请求到来时运行。实际来源必须来自已发布目录，校验模型identity/TP/generation/epoch。若运行资源变化，使用仍合法的计划或重新规划，不使用过期地址。

支持解释“为什么从这里取”：命中的副本、字节量、资源瓶颈、预测时间、实际策略。不得把规划用候选副本当作已经存在的物理副本。

**交付/验收**：同一输入可生成并应用计划，恢复到正确模型；过期计划被拒绝或显式重算；不反复构建整个placement。

## 9. 阶段七：反馈、稳定性与收益门槛

**目的**：知道模型错在哪里，并避免稍有测量波动就来回搬权重。

每次记录完整加载、搬运、准备、rank错峰、来源字节、空间高水位、建立/迁移/校验时间。预测与实测在同一口径对比。

第一版先做离线反馈报告和显式更新，不自动用一个样本覆盖全部带宽参数。随后增加最小收益门槛、最短保持时间、迁移量上限；有恢复频率数据后，再权衡未来收益和增量迁移成本。

控制器预热状态必须对齐：冷启动比较双方均冷，常驻Keeper恢复比较双方同样预热。不能把首次SciPy导入、IPC映射变化冒充placement收益。

**交付/验收**：预测—实际报告、无收益布局可保持不动、错误预测可追溯、不丢弃负结果。

## 10. 最小真实验收矩阵

| 场景 | 要证明的能力 |
| --- | --- |
| 单模型、单目标、两卡对称 | 自动候选→MILP→布局变更→真实恢复闭环 |
| 放开单卡缓存上限 | 真正比较8+0、4+4及其他可行配置 |
| 两卡预算或路径不对称 | 不机械均分，能解释倾斜分配 |
| 两个可选恢复位置 | 同一placement权衡互斥未来场景 |
| 临时空间不足 | 迁移全过程不超预算、始终保留有效覆盖 |
| 中途失败/worker代次变化 | 不发布坏副本、可恢复/可重试、拒绝过期计划 |

优先CPU小规模枚举、模拟资源变化和故障注入。真实模型每代表性方案通常一次、必要时二次；不能恢复五轮默认。全量权重与生成检查继续保留，明确位于加载计时之外。

## 11. 推荐落地顺序与首个交付

首个交付聚焦阶段1/2/4/5/6的单目标闭环，使用阶段3现有局部成本模型并明确局限，同时提供阶段7的只读报告。之后补非对称预算，再扩多恢复目标与反馈重规划。

代码归属：产品能力进`main_lib/fluidckpt/cluster`及相关memory/executor模块；驱动、故障测试和分析进`codex_coding/src`；原始结果进`codex_coding/results`。本计划提出的结构名可在实施时细化，不要求先做大规模重构。

完成定义：用户给模型、预算和目标，系统无需人工挑位置/改脚本即可生成计划、检查预算、改变布局、恢复并产出可解释报告。吞吐或恢复更快是待检验结果，不以人为挑选样本作为完成条件。
