## 1. 下一阶段要解决的问题

第一阶段已经证明：将处理后的模型权重主动保存在指定NUMA内存，可以释放GPU后正确恢复，并显著缩短当前配置的权重加载时间。

但当前每个rank只有一个实际本地来源，规划器没有实质的来源选择空间。第二阶段要建立：

> 一段权重可以拥有多个明确、有效、可访问的副本；规划器据此选择来源和字节分配；执行器按计划真正并发搬运；测试平台能够区分副本放置、复制实现和流规划各自的收益。

本阶段首先在node27的单机两卡、多个受控DRAM区域上完成。跨节点、GPU显存副本、联合副本放置优化作为有明确门槛的后续扩展，不在单机结果上直接宣称成立。

### 1.1 系统论文定位

FluidCKPT定位为**面向大模型推理的、拓扑感知的权重保活与快速物化系统**。“物化”指把已保存的数据变成指定GPU上可用于推理的参数及必要派生状态。

主要研究问题：在实际内存容量、传输带宽和共享资源限制下，如何安排权重副本及其恢复，让所有目标GPU尽早完成权重准备？

主指标保持为权重加载时间，不把进程启动、Python导入、HTTP就绪或持续推理吞吐变成主优化目标。实际生成请求作为正确性与兼容性检查保留。

### 1.2 本阶段要检验的假说

| 假说 | 需要的证据 | 不能作为证据的现象 |
| --- | --- | --- |
| H1：主动管理副本位置能改变竞争关系 | 相同数据/容量/执行器下，只改变NUMA布局，测共享资源与完成时间 | 同时换分配器、复制实现和布局后得到一个更快结果 |
| H2：共享资源规划优于独立选最快来源 | 固定副本与执行器，在预先定义的竞争场景及保留验证场景比较 | 用额外副本对比没有副本的基线，或人为把基线做慢 |
| H3：执行器能兑现计划分配 | 实际来源字节、提交顺序、完成事件和并发区间符合计划 | 只看到两个线程或两条CUDA stream已经创建 |
| H4：准备成本可能抵消多路径收益 | 分开测映射、规划、缓冲、复制、同步，比较完整加载窗口 | 单独比较复制带宽，隐藏了新增路径的准备成本 |
| H5：额外副本有容量与复用次数边界 | 报告副本建立成本、实际内存、重复恢复的总成本 | 只报告一次恢复更快，不计保活副本成本 |

允许出现“在当前单机两卡条件下，多路径没有额外收益”的结论。平台能准确证明这一点，同样是有效交付；不能为了正向结果删除负对照或劣势样本。

## 2. 当前事实、纠正项与代码缺口

### 2.1 当前实测基线

模型为Qwen3.6-35B-A3B，node27上TP=2，每个rank约32.75 GiB；总权重快照70,329,718,112字节，约65.50 GiB。

| 方案 | 样本数 | 加载中位数 | 最小～最大 | IQR/中位数 |
| --- | ---: | ---: | ---: | ---: |
| 普通文件加载 | 5 | 19.644秒 | 16.957～22.032秒 | 16.59% |
| NUMA DRAM＋中转复制＋LP | 5 | 1.744秒 | 1.564～2.189秒 | 13.86% |
| NUMA DRAM＋直接填充＋LP | 5 | 1.620秒 | 1.461～2.607秒 | 1.65% |

- 10次恢复全部逐字节一致，固定输入的生成结果一致。
- 正式验证中的副本建立耗时14.07秒；两个Keeper合计PSS约69.17 GiB。
- 直接恢复的一次2.607秒慢样本，目标准备/映射阶段达到约1.227秒；复制段并未相应变慢。具体慢调用根因尚未证明。
- 直接恢复的中央波动通过原计划10%门槛，但只有5次样本，不能据此声称尾延迟稳定；普通加载和中转恢复未通过该门槛。
- 普通文件加载前，全部权重文件页驻留比例约94.8%～97.7%；这不是严格全冷或全热缓存实验，也不等于实际读取路径的精确命中率。
- 现有约12倍中位加速是保活恢复相对普通文件加载的整体收益，不是多来源流规划的收益。

### 2.2 拓扑事实与历史假设修正

- node27目前系统报告1个socket、128个CPU逻辑处理器、8个NUMA节点；不能沿用旧资源模型中“NUMA 0～3与4～7分别属于两个socket”的硬编码假设。
- GPU运行时编号、DRM编号通过PCI BDF对齐。当前GPU 0对应`card1`/NUMA 0，GPU 1对应`card2`/NUMA 3。
- 每NUMA约63 GiB可见DRAM，每卡约64 GiB可见显存。容量与可用量不同，每次运行重新核对。
- 现有受控测试中，单路近端和所测远端路径均约48.6 GB/s；两卡各用近端区域时仍各约48.6 GB/s；两卡同时读NUMA 0时分别约28.8与28.2 GB/s。
- 这些并发实验说明存在共享瓶颈，但尚不能仅凭一组数据把56.9 GB/s认定为固定、普适的“内存控制器容量”。
- HSW显示GPU间可达，不代表任意并发组合有可叠加带宽。四个高速端口当前报告InfiniBand、400 Gb/s；标称链路速率不能替代端到端实测。

## 4. 数据模型与生命周期

### 4.1 稳定的权重身份

以处理后的权重快照为基础，标识至少包含：

```text
ModelIdentity:
  model/config identity, dtype, TP size, rank,
  layout version, required postprocessing/adapter version

WeightRegion:
  region_id, model_identity, rank,
  logical_offset, logical_length,
  storage/tensor layout reference

Replica:
  replica_id, generation, region coverage,
  owner_worker, node, numa/tier/device,
  allocation owner, allocated_bytes, valid_bytes,
  state, read_leases, integrity information
```

第一阶段的模型身份包含配置/索引内容及文件大小/mtime，不能把它称为全权重内容哈希。第二阶段区分声明身份、文件元数据指纹与实际内容完整性；小数据使用确定性内容和全量比较，大模型记录捕获来源并执行全量恢复对照，必要的块哈希计算成本单列。

模型布局必须包含dtype、shape、stride、storage offset、共享storage/别名和必要派生属性。同样字节数不代表可以互换。

### 4.2 块与区间

- 初始实验粒度取64 MiB，辅以16/256 MiB用于调参；末块保留真实长度。
- 块是逻辑区间，不要求每个块单独mmap或单独注册。可用较大内存arena容纳多个块，减少固定分配和注册开销。
- 保留`logical_offset`与`replica_buffer_offset`，禁止把全模型偏移直接用于部分副本缓冲。
- 根据各副本覆盖范围的所有边界，把需求切成“同一区间内合法来源集合不变”的区域，再交给规划器。
- 一个rank可有多个区域需求，故不能继续以`tp`作为需求唯一键。
- 拷贝到目标时，通过现有storage索引映射实际参数位置；跨storage边界的块必须完整覆盖，不假设一个块只对应一个tensor。

### 4.3 副本状态与租约

```text
ALLOCATING → COPYING → VERIFYING → VALID → RETIRING → RELEASED
     │           │          │
     └───────────┴──────────┴────→ FAILED
```

- 只有完整验证并原子发布的`VALID`区间才能参与规划。
- 规划确认后持有来源读租约；实际执行前再次核对generation，防止“规划时存在，执行时已释放”。
- `RETIRING`停止接收新租约，已有传输结束/取消并同步后才释放。
- 取消和失败不能立即解除注册或unmap仍在被DMA访问的缓冲。
- worker异常退出使其副本失效，不宣称DRAM保活具备持久化或故障容错能力。
- IPC导出只导入一次，复用既有映射进行校验；不得再次消费同一引用计数来模拟新的映射。

## 5. 容量预算与副本构建

### 5.1 先小数据，后真实模型

小规模测试每rank先使用1～4 GiB确定性数据，各块内容随rank/region变化。不能像旧吞吐测试那样反复复制同一个缓冲，之后却声称整个模型恢复正确。

真实模型基础副本约65.50 GiB。每NUMA约63 GiB，不能把两份完整rank（约65.50 GiB）都放在一个NUMA节点，也不能默认两个NUMA区域能容纳两份完整模型及预留空间。

初始额外副本预算使用0、4、8 GiB三个档位，按区域选择第二来源，并重新检查每个NUMA的实际容量。该预算是实验配置，不是预先保证一定可用的资源。

### 5.2 预算必须包含真实成本

- 原有副本、额外副本、对齐浪费、注册区域、构建时暂存和在途块。
- 目标GPU权重、已有Keeper显存、复制暂存与验证缓冲。
- PSS、内存映射与实际分配量分别报告，不能将共享页重复计数。
- `MemFree + FilePages`等只是容量预检估计，不等于所有缓存都可立刻回收；预检通过后仍须处理分配失败与资源变化。

副本建立先从已验证的DRAM副本读取，不重新打开模型文件混入额外文件缓存因素。记录复制、触页、注册与验证成本；构建期间源副本持有租约。

## 7. 真实多路径执行器

### 7.1 并发结构

当前`run_local()`对所有本地操作顺序执行。新执行器将准备阶段与执行阶段分开：

1. 核对计划、获得来源租约。
2. 每个目标storage的IPC映射只建立一次。
3. 按合法路径建立有界队列/stream，登记共享资源预算。
4. 以字节量和计划比例交错提交块，控制每条路径在途数量。
5. 等待所有相关完成事件，确认目标覆盖完整。
6. 发出本次generation的`weights_ready`，再释放读租约和临时资源。

第一版不进行任意失败重试。失败时取消整次加载、等待已提交传输结束、回收资源并明确失败。后续若增加重试，必须有generation和区间提交状态，防止旧任务继续写入新目标。

### 7.2 并发不等于带宽相加

- 两条DRAM来源进入同一GPU，通常仍共享GPU入口或复制资源。即使stream并发，总速度也可能没有增加。
- CPU循环调用的先后、CUDA/HIP stream依赖、设备复制引擎和序列化开关，都可能限制实际并发。
- 初始保持`AMD_SERIALIZE_KERNEL=3`与已有基线一致。如果它限制待验证的并发机制，单独设计控制变量测试；确认关闭后正确，再为所有算法一起重建基线，不能只对优化方案关闭。
- 记录实际提交/完成时间与重叠区间。GPU events用于对应stream内的设备操作，跨stream须结合依赖关系；CPU线程存在不能作为并发证明。
- 调度份额按字节或成本权重计算，大小不同的块不能仅按块数分配。
- 对共享资源实现背压或限速，避免短时间提交量远超可用容量。

### 7.3 计时细化

保留当前统一加载指标，新增来源查询、目录校验、租约、规划、目标映射、缓冲准备、提交、复制、同步和完成通知事件。

映射慢样本诊断使用有开关的细粒度探针：pickle/manifest处理、设置设备、各storage IPC导入、view构造及必要同步。避免默认每次大量打印；探针开销单测，正式性能数据使用相同探针配置。

当前控制器存在等待handoff的轮询。记录`target_exported → execute_begin`的控制等待；若改用事件通知或缩短轮询，对所有候选算法一致修改并重建基线。

## 8. 流模型与求解

### 8.1 主指标和连续模型

设需求区域i大小为`D_i`，合法路径集合`P_i`。`x_ip`表示区域i沿路径p搬运的字节；`B_p`表示路径上限；`C_r`表示共享资源r的容量；`a_rip`表示资源消耗系数。

```text
minimize T
  sum(p in P_i) x_ip = D_i                    for every region i
  sum(i using p) x_ip <= B_p * T              for every path p
  sum(i,p) a_rip * x_ip <= C_r * T            for every shared resource r
  x_ip >= 0
```

不同rank和不同区域保持独立身份。LP分配结束后再分配具体非重叠逻辑字节区间，处理对齐和尾块，并重新验证覆盖及资源负载。

带宽用bytes/s或统一GB/s，容量用bytes；bit与byte不得混用。不要把文件大小、处理后快照大小和实际传输字节混成同一个分子。

### 8.2 模型校准

- 单路数据拟合固定成本与大块带宽，跨CPU域/NUMA的标签来自当前探测结果，不使用旧socket表。
- 并发实验校准哪些路径共享资源、是否存在方向/组合依赖；容量不一定是全局恒定值。
- 只在已验证的并发区间使用模型；无法解释的组合先标记不支持或保守回退。
- 有固定开销的路径组合先小规模枚举，然后在组合内求连续分配。初始化共享一次的成本不能按块重复累计。
- 加入与实际执行器一致的并发上限、暂存容量和依赖；忽略固定成本的LP值只作为模型下界。
- 不把同一GPU的两个DRAM来源带宽简单相加；也不把4条400 Gb/s链路的标称总和直接当作可用应用吞吐。

### 8.3 求解预算与对照

保持已有5秒求解超时作为兜底上限；对于只有约1～2秒的加载，必须检查规划是否划算。小问题目标是预热后规划中位数≤50 ms且不超过总加载时间的5%；未达到时优先缓存布局无关预处理、缩小候选或回退，不隐藏实时规划成本。

至少保留以下策略：固定合法来源、NUMA就近来源、单路最快来源、资源贪心、共享资源LP。单路速度差异落在测量噪声内时采用预先规定的稳定tie-break，例如先近端、再固定副本ID，不能利用噪声故意让基线选错。

LP超时、输入过期或无可行解时只回退到已验证的合法计划；没有有效来源则明确不可加载。结果记录实际执行的策略，不能把fallback结果标成LP成功。

## 9. 实验场景与消融矩阵

### 9.1 先验证机制，不预设每个场景都能加速

| 场景 | 布置方式 | 目的与预期 |
| --- | --- | --- |
| C0：单来源回归 | 每rank一个近端DRAM副本 | 新目录/执行器不破坏已有正确性；规划退化为原路径 |
| C1：单GPU双DRAM来源 | 小规模相同区域在两个NUMA上有副本 | 共享GPU入口负对照；不能预测两倍带宽 |
| C2：双GPU各自近端 | 两个目标使用不同近端NUMA | 已接近局部最优的负对照；LP不应凭空产生收益 |
| C3：双GPU争抢一个NUMA | 小规模两份不同分片在同一NUMA，可选区域有另一NUMA副本 | 测量共享竞争与分流能力；不使用放不下的全量布局 |
| C4：覆盖不完整 | 只有指定4/8 GiB区域拥有第二来源 | 验证部分副本、来源集合切分和正确偏移 |
| C5：不对称需求/候选 | 需求量或合法来源集合不同，布局预先定义 | 比较全局协调与独立选源，允许简单策略已足够好 |
| C6：故障与容量限制 | 失效副本、错误版本、缺块、注销中断、预算不足 | 禁止成功标记；资源可回收；下一次运行不受污染 |
| C7：真实Qwen权重 | 基础副本65.50 GiB，部分额外副本，TP不变 | 验证真实参数及推理，不能用吞吐假数据代替 |

两张GPU各自使用近端DRAM时，现有实测已可同时接近单卡上限。该场景本身可能没有可供LP获得的带宽收益。不能通过强制基线绕远路制造“优化成功”；若双卡DRAM场景没有真实改进空间，报告机制边界，再评估是否需要更多目标或互补资源路径。

### 9.2 三组独立消融

| 消融 | 固定项 | 唯一主要变化 |
| --- | --- | --- |
| A：副本布局 | 执行器、规划策略、总副本字节预算 | 数据放在哪些NUMA区域/哪些块有额外副本 |
| B：规划策略 | 副本位置、内容、执行器、计时与并发配置 | 固定/就近/最快/贪心/LP |
| C：执行调度 | 固定计划、来源区间、目标布局 | 串行执行与受限并行；同一复制实现 |

不同内存预算的比较另列“容量—性能曲线”，不能并入等预算放置消融。直接填充与中转复制也应单独比较，不与规划变更同时进行后归因。

### 9.3 稳定性与统计

- 初步每场景至少5次；拟用于核心性能论点的场景至少10组配对/交替运行，并保留固定随机种子。
- 测试场景在观察结果前固定，训练/校准与保留验证分开，避免只展示最有利的一种布局。
- 报告中位数、每次值、最小/最大、IQR/中位数、失败率；样本不足不宣传p99。
- 目标仍为IQR/中位数≤10%，但不能用该指标掩盖单个尾部慢样本。映射异常保留并解释，不从主要结果删除。
- 改善判断应同时超过噪声、包含规划与准备成本，并在配对结果上成立；建议以至少10%的中位改善作为值得继续优化的工程目标，不将其当作保证。
- 若没有显著改善，给出瓶颈、模型预测、实际数据与负结果；不为达标更换有利分母或挑选基线。

## 10. 计时、正确性和成本口径

### 10.1 统一计时

继续使用同机时钟：

`T_load = max(weights_ready[rank]) - min(load_begin[rank])`。

区间包括本次加载所需的目录查询、校验、动态规划、模型结构/目标缓冲准备、映射、复制、数据相关后处理与最终同步。首次求解器初始化若发生在区间内也要计入，并同时记录冷/暖状态。

通用离线测量、可复用副本准备与预先建立的通道可单列，但必须披露其成本和复用条件。不能只把优化算法的模型专用准备移到计时外。

### 10.2 正确性

- 小数据按rank和region生成不同确定性内容，避免“重复搬同一块”也能通过校验。
- 检查来源区间、目标区间、版本、dtype/shape/stride/别名；GPU上的每个必需字节恰好被有效操作覆盖。
- 真模型在性能计时外做全量字节对比与固定生成请求对照。
- 只有所有路径完成且同步后才发布ready；线程创建成功、任务提交成功或单一路径完成都不算成功。
- 故障注入应包含错误模型同尺寸副本、错rank、缺少尾块、重叠写、source offset错误、目录过期、复制失败和释放竞争。

### 10.3 容量与总成本

记录：逻辑权重、物理保留内存、额外副本、临时缓冲、每条来源真实提供字节、H2D/D2D/网络字节以及数据回收情况。

对复用K次的方案同时报告：

`总成本 = 初次捕获 + 额外副本建立 + K次完整加载成本`。

若相对基线每次节省`ΔT`，只有`ΔT>0`时才讨论额外副本成本的摊销次数；不得忽略内存占用及对其他任务的资源代价。

## 11. 实施顺序与阶段门槛

| 阶段 | 建设工作 | 通过条件 | 失败后的动作 |
| --- | --- | --- | --- |
| S0：基线与观测补齐 | 修正socket假设、补映射与控制等待计时、记录软件/拓扑指纹 | 新旧计时可解释；原单来源恢复仍正确；不掩盖慢样本 | 回到单来源最小复现，不启动多路径优化 |
| S1：区域与副本目录 | 独立副本ID、generation、部分覆盖、源偏移和租约 | C4/C6小数据通过；没有未验证副本进入候选 | 修正身份和生命周期，不跑大模型 |
| S2：受控副本构建 | 每副本指定NUMA、预算检查、位置验证与回滚 | 多个小副本真实内容正确，注销后无残留，CPU内存分配可解释 | 缩小工作集，核对页位置和注册/释放顺序 |
| S3：真实并行执行 | 改造串行local loop，增加路径队列/stream、在途限制、完成依赖 | 固定手工计划可执行，来源字节与目标全量一致，能观测并发或解释硬件串行 | 优先排查执行器，不修改求解器来掩盖执行问题 |
| S4：资源标定与规划 | 测关键竞争组合，接入区域LP及基线策略 | C0～C5均合法；共享瓶颈负对照不虚构增益；保留验证误差可解释 | 修正模型或缩小支持范围，保留合法简单策略 |
| S5：真实模型与消融 | C7全量权重、A/B/C消融、重复统计 | 全量恢复正确，记录成本；收益与无收益场景均可复现 | 正确性失败先停性能结论；收益不显著则报告边界 |
| S6：扩展决策 | 评估4卡、更异构来源或跨节点的必要性 | 单机接口稳定且有真实瓶颈证据支持扩展 | 不因“需要展示最大流收益”而盲目扩大规模 |

资源模型阶段建议以保留集完成时间预测误差中位数≤10%为目标；超过20%的样本逐项解释或将相应组合标为不支持。纯带宽模型的下界不能冒充包含映射的完整加载预测。

功能交付完成不等于规划性能论点已证实。D1～D5通过代表平台具备多来源实验能力；只有S5消融数据才能支持H1/H2等性能结论。

## 13. 后续扩展条件

### 13.1 GPU显存与跨节点来源

如果单机DRAM场景受同一GPU入口限制，且各目标已使用独立近端DRAM，那么再增加DRAM来源可能无法提升带宽。这时可评估互补的GPU互连来源或跨节点源，但必须重新测资源是否独立，不能凭接口名称假定带宽可叠加。

跨节点先两机、再三机；探测每台机器自身的拓扑，核对传输原语。不同机器的单调时钟不能直接相减，集群计时使用协调器窗口并报告消息延迟/时钟误差。

HIP IPC不跨机器；跨节点权重数据必须通过真实网络传输。当前已知环境优先使用验证过的集合通信，并保证各参与者一致的操作顺序。

### 13.2 联合放置优化

只有固定布局下的执行与模型经过验证后，才将“是否增加副本、放在哪里”加入离散决策。先枚举小规模候选，必要时再引入MILP；等预算比较，报告构建与摊销成本。

### 13.3 推理框架自身保活基线

保留SGLang普通加载作为背景对照，但不能拿它代替原生保活基线。另行核实当前版本和依赖，建立同样的数据状态、显存释放要求和准备成本口径；不可运行时明确标记缺失。

## 14. 预期效果与最终交付说明

本阶段预期首先获得的是**可选择、可执行、可解释的多来源加载能力**，而不是预先承诺一个比1.62秒更低的数字。

最终报告必须回答：

1. 哪些权重区域拥有多个合法来源，副本实际放在哪里？
2. 各路径共享什么资源，哪些组合确实能够并行？
3. 计划分配的字节是否被执行器真实兑现？
4. 固定副本条件下，规划相对就近/最快源是否有额外收益？
5. 等预算改变布局后，收益与成本分别是多少？
6. 映射和调度成本是否抵消带宽收益，最慢rank受什么限制？
7. 在哪些场景无收益、模型失效或容量不允许？

不使用“LP已经接入”替代真实性能证据；不使用“数据在DRAM”替代位置与版本验证；不使用“最终回答看起来正常”替代全量权重校验。

执行期间按授权范围推进开发、验证和可逆修复；阶段门槛是技术验收，不新增逐步审批流程。若出现需要改变任务范围、额外长期占用资源或不可逆操作的情况，再说明具体原因与用户讨论。
