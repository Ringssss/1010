## 1. 本轮已经形成的判断

SGLang 和 Janus 是核心对照。若论文强调拓扑感知的权重布放与恢复，BlitzScale 是必须深入对照的方法线；ServerlessLLM 必须进入相关工作，并按最终收益来源确定实验深度。强简单分层策略始终保留，用于区分系统能力与求解器增量。

“核心对照”表示必须回答其代表的比较问题，不等于立刻完整移植对方全部系统。原版运行、硬件适配和共同执行器上的机制对照承担不同的证明任务，应分别命名和报告。

保活、IPC、多层缓存、跨服务器搬运、NUMA 亲和性和拓扑感知分发均有已有工作。本文定位是一项待验证的具体研究问题，不构成“上述系统均未考虑”或“首次”的结论。我们需要找出明确条件下的决策、能力或资源代价增量，并用真实恢复结果验证。

目前最值得检验的因果链为：

**各位置保活预算 → 哪些权重块能保留在哪里 → 恢复时可选择的来源 → 共享资源负载与执行依赖 → 最后一个必要 rank 权重可用。**

其中，复杂拓扑是现实约束，联合规划是候选方法；二者都不能替代主指标收益。简单策略足够时直接采用，不为保留 MILP 名称持续增加有利场景。

| ServerlessLLM | 多层加载、缓存局部性与启动选址 | 收益是否由已有缓存/流水/位置感知方法解释 | 相关工作必纳入；若最终核心收益与其决策直接重叠，补适用策略或系统对照 |
| 强简单分层策略 | 远端感知选源、TP 成组候选、预算受控缓存 | 复杂规划相对充分利用同一底座的简单算法有何增量 | 已有 paired/marginal greedy 与 fastest 等路径；保留合法远端、IPC 和候选机会，不弱化对手 |

### 2.1 三类实验身份

| 身份 | 命名方式 | 允许支持的结论 |
| --- | --- | --- |
| 官方实现，固定版本且完成验收 | 系统名 + commit/版本 + 配置 | 冻结条件下的系统比较 |
| 在官方实现上进行硬件改造 | 系统名 + HIP/海光适配版 | 明确适配范围和行为变化内的实现比较 |
| 在共同执行器重建某项机制或策略 | Janus 式 warm/D2D 机制对照；依据 BlitzScale 的策略适配 | 相同底座下该机制/策略的比较 |

采用共同执行器可以控制格式、传输后端和引擎差异，但必须保留所比较方法的关键能力。仅移植一个弱化规则的结果不能代表原系统；若方法依赖提前部分服务或自由选址，应保留其能力的说明，并限定本次比较所能回答的问题。

当前我们的强 greedy 不是 BlitzScale 复现。HIP IPC 适配也不是原版 SGLang daemon。没有运行的对照标为未测；确实违反共同预算的配置标为不可行，并保留其合法后备路径，不用“无穷慢”替代尚未完成的适配。

## 3. 各系统的能力、可复用点与具体差异

### 3.1 SGLang：设备常驻权重共享

SGLang Weight Cache Daemon 将处理后的 TP 权重保留在设备内存中，由新引擎通过 IPC 接入。这避免再次读取 checkpoint 和重复权重处理。该路径需要兼容的权重、布局与运行环境，初次建立缓存也有成本。[官方介绍](https://www.lmsys.org/blog/2026-08-21-sglang-fast-recovery/)

本项目此前核查的代码版本为 `70f0b7351e74b372cc928db533824d3993d65922`，入口包括 [daemon.py](https://github.com/sgl-project/sglang/blob/70f0b7351e74b372cc928db533824d3993d65922/python/sglang/srt/weight_cache/daemon.py) 与 [ipc_loader.py](https://github.com/sgl-project/sglang/blob/70f0b7351e74b372cc928db533824d3993d65922/python/sglang/srt/weight_cache/ipc_loader.py)。博客与固定代码的 daemon 生命周期、失效处理和回退语义存在差异，运行协议以选定代码为准；详见正式计划15.4节。上游后续路线图与已验收实现分开记录。

**复用重点：**保存者/使用者分离，处理后格式，兼容性检查，目标设备已有权重时的 IPC 直接绑定。FluidCKPT 和强简单策略都应获得合法 IPC 机会。

**待验证差异：**完整权重无法长期留在目标 HBM，或恢复目标改变时，如何利用其他位置的有限空间安排块驻留与恢复。HBM 足够且权重已经就位时，IPC 是强速度参照；不承诺搬运路径普遍胜过直接共享。

### 3.2 Janus：支撑在线服务的生命周期与快速复制

Janus 面向多模型在线服务，通过模型共置、扩缩容、请求调度和 xTensor 资源管理提高服务达标率与设备利用率。保活是关键支撑机制。其论文定义 active/warm/cold，并提供 host wakeup 与活跃实例 D2D fork；部署包括同一高速 supernode 内跨服务器复制。[论文](https://yangtonghome.github.io/uploads/Janus_SOSP2026.pdf)、[官方仓库](https://github.com/Janus2026/Janus)

本轮核查代码为 `ec1beca2dbef5628b38e266fdc9afa0dba451678`，得到以下与保活最直接相关的事实：

| 已核查机制 | 边界 | 代码证据 |
| --- | --- | --- |
| host pinned cache 的复用与引用计数 | 解决缓存共享和所有权；没有在该类中展示显式字节预算下的驻留选择 | [pinned_host_memory_cache.cpp](https://github.com/Janus2026/Janus/blob/ec1beca2dbef5628b38e266fdc9afa0dba451678/janus_engine/janus/core/layers/npu/loader/pinned_host_memory_cache.cpp) |
| LIGHT_SLEEP 保留 host 权重，DEEP_SLEEP 重新加载路径 | 常规 service sleep 固定发送 LIGHT_SLEEP；不据状态枚举推断已有预算驱动冷热控制 | [worker_impl.cpp](https://github.com/Janus2026/Janus/blob/ec1beca2dbef5628b38e266fdc9afa0dba451678/janus_engine/janus/core/runtime/worker_impl.cpp#L726)、[model_instance_mgr.cpp](https://github.com/Janus2026/Janus/blob/ec1beca2dbef5628b38e266fdc9afa0dba451678/janus_service/janus_service/scheduler/managers/model_instance_mgr.cpp#L163) |
| D2D 从多个候选中选一个逻辑源实例 | 选择最高 EPDT 的候选以减少源即将被排空的风险；TP 按 rank 对应复制，不是同一块的任意多源组合 | [instance_mgr.cpp](https://github.com/Janus2026/Janus/blob/ec1beca2dbef5628b38e266fdc9afa0dba451678/janus_service/janus_service/scheduler/managers/instance_mgr.cpp#L2943)、[llm_engine.cpp](https://github.com/Janus2026/Janus/blob/ec1beca2dbef5628b38e266fdc9afa0dba451678/janus_engine/janus/core/distributed_runtime/llm_engine.cpp#L1381) |
| weight_segments 支持非连续来源区段 | 分段内存描述不等于预算驱动的独立块布放；目标端按源区段顺序填入 | [worker_impl.cpp](https://github.com/Janus2026/Janus/blob/ec1beca2dbef5628b38e266fdc9afa0dba451678/janus_engine/janus/core/runtime/worker_impl.cpp#L776) |
| 页回收至 xTensor 共享池 | 池内模型可复用，不等于任意外部进程已获得物理显存 | [phy_page_pool.cpp](https://github.com/Janus2026/Janus/blob/ec1beca2dbef5628b38e266fdc9afa0dba451678/janus_engine/janus/core/framework/xtensor/phy_page_pool.cpp#L247) |
| CUDA 路径已有 NUMA 映射与亲和性 | NUMA 绑定本身不能作为 Fluid 独有能力；需比较预算下的块位置选择 | [dist_manager.cpp](https://github.com/Janus2026/Janus/blob/ec1beca2dbef5628b38e266fdc9afa0dba451678/janus_engine/janus/core/distributed_runtime/dist_manager.cpp#L78) |

**复用重点：**缓存身份结构、请求排空、复制期间源端保护、失败回退、运行时复用。与我们已有 lease、目录和执行器能力逐项映射，避免新建同功能组件。当前 remote wakeup 受 `USE_NPU` 限制，直接移植到海光需后端适配；主机缓存的键也不能直接当作不可变内容版本证明。

**待验证差异：**暂停期间如何按位置预算选择保留子集，并在恢复时组合有效来源、考虑共享资源。该代码审查支持指出未展示的决策层，不支持宣称 Janus 无 placement、无 NUMA、无跨节点或完全不考虑服务干扰。

### 3.3 BlitzScale：参数池与拓扑感知扩容

BlitzScale 已讨论参数缓存空间与扩容速度之间的权衡，具有长期 GPU/CPU 参数池和拓扑感知分发。其 live scaling 允许权重尚未全部到齐时参与部分计算，不能把全部权重到齐时间直接等同于其服务收益。[论文，重点§5.1与§5.3](https://www.usenix.org/system/files/osdi25-zhang-dingyan.pdf)

**复用重点：**来源组织、拓扑分组和适用的贪心分发方法。先检查我们是不同 TP 内容的单次恢复、互斥未来目标，还是相同内容的同时扩容；这三种需求不能直接套用同一个组播算法。

**待验证差异：**其参数池维护与分发，在本项目显式位置预算和给定目标下是否已经足够。论文的聚合 host memory 足以缓存模型集合的前提，应与我们的预算范围逐项对齐。当前固定完整 DRAM 底本的 e6 不能据此声称已经解决“聚合 DRAM 不足”的更广问题。

### 3.4 ServerlessLLM：多层加载与局部性

ServerlessLLM 将加载优化、多层缓存和位置感知调度结合起来，已有缓存布放与替换讨论。[论文](https://www.usenix.org/system/files/osdi24-fu.pdf)

**复用重点：**多层加载的流水思想、缓存局部性和加载代价估计。若我们的最终收益主要来自这些能力，应补适用的机制或系统比较。

**待验证差异：**明确目标设备组受外部什么约束，再比较驻留和恢复决策。不能剥夺对手合法选址自由后，把差距写成加载算法优势；固定目标的子问题比较应明确标注。

## 4. 论文如何介绍相关工作并呈现 delta

相关工作按所解决的问题组织：设备权重共享 → 多层加载与缓存 → 在线弹性和权重分发 → 通信规划方法。每组先说明已有贡献，再引出本项目不同的决策对象与约束。详细公式与算法放方法部分，性能优越性放实验部分证明。

### 4.1 可复用的中文表述草稿

**SGLang：**SGLang Weight Cache 通过独立进程保留处理后的设备权重，并以 IPC 支持引擎重新接入。FluidCKPT 研究保活空间受限或恢复位置变化时的权重驻留与恢复组织，将设备常驻共享作为可用恢复路径之一。

**Janus：**Janus 面向多模型在线服务，将资源共享、模型生命周期与快速副本激活结合起来。FluidCKPT 聚焦暂停期间的块级驻留决策：在显式位置预算下选择保留内容，并根据恢复目标与共享通信资源组织取数。

**BlitzScale：**BlitzScale 利用集群参数池和拓扑感知分发降低扩容开销，并通过逐层协作提前提供计算能力。FluidCKPT 研究位置预算约束下的驻留与取数联合决策，以全部必要权重可用时间衡量恢复；两者在可用来源、预算前提和服务终点上的区别需在实验设置中明确。

**ServerlessLLM：**ServerlessLLM 通过多层加载和位置感知调度利用缓存局部性。FluidCKPT 在给定恢复设备约束下研究暂停权重块的保存与恢复，评估共享资源和位置预算如何影响该决策。

**综合引出本工作：**已有系统通过设备常驻共享、多层缓存加载、活跃副本复制和拓扑感知分发降低模型激活成本。FluidCKPT 研究这些机制之上的驻留决策：当暂停模型只能使用有限且分布不均的保活空间时，如何选择权重块的保存位置，并结合恢复需求与共享通信资源组织取数。

这些是问题定位草稿。只有得到公平对照下的能力或效率证据后，才能追加“改善多少”“在哪些条件下优于何种方法”等结果句。

### 4.2 需要避免的模糊差异

| 不采用的表述 | 应说明的具体区别 |
| --- | --- |
| 已有工作均不做保活或长期 placement | 指出已有缓存/参数池，再对齐保留粒度、预算对象、目标和决策方法 |
| Janus 单机、无 NUMA、只有一张源 GPU | 它已有相应能力；D2D 是一个逻辑实例的 TP 对应复制 |
| 我们首次使用多源、复杂拓扑或最大流 | 引用已有通信理论，验证其在预算驱动驻留决策中的具体作用 |
| 用 MILP 就比启发式好 | 同候选、同来源、同执行器实测；同解时承认没有该项算法增量 |
| 更综合，所以论文贡献更大 | 说明新增约束改变什么选择、带来什么独立收益 |
| 机制适配优于对照，所以整个系统优于 Janus | 结论限定到实际实现及指标；完整服务系统比较另需协议 |

本篇论文不必把底层每个机制都包装成创新。权重对象与执行器可以作为正确性和可实施性基础；候选核心贡献集中在驻留—恢复耦合及其资源权衡，是否成立须由公平对照验证。

## 5. 公平比较协议：先冻结这些条件

1. **身份与格式：**同模型版本、dtype/量化和固定 TP；记录原始 checkpoint 与处理后快照。不能只给 Fluid 提供预处理格式却把另一方重复处理时间全部解释为规划收益。完整系统比较与同底座决策比较分别报告。
2. **主指标：**同目标主机 `max_rank(weights_ready) - min_rank(load_begin)`。跨主机 TP 使用每主机窗口和协调器 all-ready 窗口分别报告，不减未校准的跨机 monotonic 时间。权重就绪、进程启动、首 token 和 SLO 是不同指标。
3. **计时边界：**明确规划、prepare、传输、验证、发布哪些在窗口内；另报窗口外建立成本。不能为某个算法隐藏在线求解或准备开销；别名结果不当独立测量。
4. **资源账本：**完整底本、额外缓存、目标分配、暂存和迁移峰值分别列；同时记录总物理占用与新增占用。固定底本仍需计账，不因所有方案相同而从总成本消失。
5. **活跃源：**若其本来就在服务业务，不将全部现存权重当作 baseline 新增保活成本；同时报告源端复制干扰。若为保证恢复而专门启动、延迟排空或延长源实例存活，应计入增量设备驻留时间、资源占用及干扰。各方法共享相同外部源可用性，复制保护、必要排空与准备成本按冻结边界报告。若没有活跃源，保留合法 host/存储后备，不直接判恢复失败。
6. **共同机会：**相同位置预算、合法来源和硬件可达性；双方都可使用 IPC 和远端。限制对手能力必须来自任务本身或明确的机制消融，不能作为默认弱基线。
7. **内存状态：**文件加载标注 Linux page cache 状态，显式 pinned DRAM 与 OS 缓存分开；NUMA 绑定和实际物理归属需检查。池内归还与对其他进程释放分开计量。
8. **正确性与回收：**内容/布局/输出、有效覆盖、lease 与实际物理释放按共同协议验收。全 SHA 不替代完整模型首次生成正确性。
9. **比较终点：**若只测原系统的恢复机制，结论限定到机制；Janus 服务 SLO、BlitzScale 提前部分服务的价值另列，不用权重到齐时间声称全面超越。
10. **建立代价：**缓存布局构建、注册和迁移都保留计时与空间记录。一次性恢复收益不等于动态累计净收益；e8 尚未执行时不能宣布回本。

## 7. 建设重点：保留三个组件，按证据补缺口

| 组件 | 已有可复用入口 | 下一步最小工作 | 新增门槛 |
| --- | --- | --- | --- |
| 权重保存与有效目录 | [owner.py](../../main_lib/fluidckpt/memory/owner.py)、[catalog.py](../../main_lib/fluidckpt/cluster/catalog.py)、[ipc_attach.py](../../main_lib/fluidckpt/serving/ipc_attach.py) | 将 baseline 的状态、来源和资源账本映射到已有对象；保留版本/覆盖/lease契约 | 仅当所需部分释放或来源表达确实做不到时补接口 |
| 驻留与恢复决策 | [planning.py](../../main_lib/fluidckpt/cluster/planning.py)、[multi_joint.py](../../main_lib/fluidckpt/cluster/multi_joint.py) | 解释e3；核对共享资源归属；建立强对照和决策差异记录 | 真实约束改变选择且可能影响T_ready，才补一个约束/评分项 |
| 恢复与迁移执行 | [worker.py](../../main_lib/fluidckpt/cluster/worker.py)、[block_migration.py](../../main_lib/fluidckpt/cluster/block_migration.py) | 确认计划能按实际并发/串行语义执行；复用已有目标导出、校验发布和迁移 | 执行限制已被证明卡住关键路径，且已有选项不足时才最小改造 |

目前 `multi_joint.py` 已有有限候选与互斥未来场景的 expected/worst 目标；它不等于多个恢复同时发生的调度器。`planning.py` 已有节点网络/NUMA DRAM/worker资源和目标串行约束，但不是完整物理交换网络图，当前估计也不覆盖所有跨pair排程等待。应先找真实缺项，避免重造“拓扑优化器”。

建议初始聚焦固定模型/TP、外部给定预算、少量给定恢复设备组。使用既有完整DRAM底本和有限额外HBM作为第一站。若最终声称更广的多层容量紧张，补一个有代表性的DRAM受限点及完整后备账本；不自动扩大为全三维预算扫描。

复杂通信方法优先复用文献中的约束、来源分组和已有算法。最大流/LP/MILP是工具；带离散驻留、多内容需求和执行依赖的问题不能未经检查直接称作普通单商品最大流。新的求解器、全局多模型调度器、任意重分片、通用容错和自动需求预测均无当前建设依据。
