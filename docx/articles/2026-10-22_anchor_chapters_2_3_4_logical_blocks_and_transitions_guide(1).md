## 2. 三章共同完成的事情

第二章先证明目标问题值得处理；第三章解释为什么存在不同的处理方式；第四章说明这种方式怎样成为真实系统。

| 章节 | 主要任务 | 读者离开这一章时应接受什么 | 本章暂不负责什么 |
| --- | --- | --- | --- |
| 第二章 | 建立场景范围和现有成本 | 浅故障普遍，保存和恢复大状态仍昂贵 | 完整提出 daemon、命名和一致性协议 |
| 第三章 | 从机会推导核心关系变化，并给最小执行过程 | 内存所有权可与 worker 分离，但还需解决身份和一致性 | 展开所有组件算法与工程细节 |
| 第四章 | 实现前章要求，补齐成本、流程和适用边界 | 真实框架如何接入、认回对象、恢复合法状态 | 代替后续实验验证全部性能承诺 |

可以把三章的中心问题写成三个连续问句：

> 第二章：这类故障常见吗，当前处理它究竟要做多少工作？  
> 第三章：这些工作在浅故障中都必要吗？应改变哪个系统关系？  
> 第四章：关系改变以后，应用如何实际、正确且低开销地运行？

这不是同一故事重复三遍。每章都在增加新的理解层次。

按我们讨论的粒度，共有十一块：第二章两块，第三章四块，第四章五块。章首的短承接句归入过渡，不再机械计数。

| 编号 | 逻辑块 | 原文位置 | 本块输出 |
| --- | --- | --- | --- |
| B2-1 | 场景与故障范围 | §2.1 | 浅故障是一类常见且具有不同恢复条件的事件 |
| B2-2 | 恢复对象、现状与成本 | §2.2 | 即使已有优化，状态保存与重建仍昂贵 |
| B3-1 | 机会与阻碍机会的根因 | §3.1 | 同一 GPU 可复用，但内存生命周期阻碍状态保留 |

| B4-1 | 总览与职责地图 | §4.1 前部 | 哪些角色承担上述要求 |

## 4. 第二章第一块：用生产现象界定目标场景

### 4.1 入口和目标

原文 §2.1 开头：

> Production GPU clusters now execute LLM jobs that span thousands to tens of thousands of GPUs; at this scale, frequent failures are an expected operating condition [11, 32].

这句话承接引言的规模背景，但没有重讲整个 LLM 发展过程。它只为本节提出观察理由：故障是大集群必须面对的运行条件。

本块的目标不是教读者完整的故障分类，而是让读者接受：

> 存在一类设备仍然可用、只需处理 worker 退出的常见事件，值得与设备破坏分别考虑。

### 4.2 内部句子如何推进

| 顺序 | 原文做法 | 推理作用 |
| --- | --- | --- |
| 1 | 说明规模下故障常见 | 建立研究故障分布的必要性 |
| 2 | 交代三个生产报告来源 | 给后续观察提供来源 |
| 3 | 列用户、运行时、软件栈、破坏性四类原因 | 帮助理解原始事件来源 |
| 4 | 分别说明三个集群的分布 | 展示观察并非只来自单一场景 |
| 5 | 按严重程度归为 destructive/shallow | 将原因描述收敛成恢复相关分类 |
| 6 | 说明生产健康监测能够支持区分 | 连接分类与实际系统决策 |
| 7 | 给出 shallow 占比 | 确认目标范围具有重要性 |

关键句是：

> Based on failure severity, these causes can be grouped into two categories:

前面的四类用于描述原因，后面的两类用于解释恢复条件。这个重新分类是一次信息收敛，不是额外增加术语。

### 4.3 图和数字怎样服务本块

Figure 1 负责展示分布，正文提供事件类别和生产场景解释，最后把数字收束到 shallow disruptions 的比例。

真正需要带走的不是每个百分比，而是“目标类别常见，而且区分方式与设备是否仍可用有关”。

本块不需要详细解释每种错误如何修复；那会使读者从恢复主线转去学习故障排查。

### 4.4 向下一块的衔接

读者已经接受 shallow disruptions 很常见，下一问题自然是：

> 它只退出 worker，为什么恢复还值得专门优化？

因此 §2.2 转向状态和恢复成本，而不立即宣布方案。

## 5. 第二章第二块：必要状态知识 → 现有路径 → 剩余成本

### 5.1 恢复对象背景不是独立百科

原文：

> The state that must be recovered differs across workloads:

训练部分介绍权重、optimizer states、跨 step 依赖以及模型规模带来的状态规模。推理部分介绍权重和 KV cache，以及 KV 对承接请求进度的作用。

句子安排的目的分别是：

- 说明要恢复哪些对象；
- 说明为什么这些对象关系到继续执行；
- 说明为什么这些对象会形成显著容量与传输代价。

作者没有在这里展开完整 optimizer 数学公式或 attention 算法，因为理解恢复成本不需要这些知识。

这些状态性质后来也会用于一致性协议，但在本块首先承担“解释恢复代价”的任务。

### 5.2 现状路径的展开

原文用一条共同流程归纳现状：

> checkpoint → restart → reload

随后分别讲训练和推理：

    训练：
    定期保存参数、optimizer state 和进度
    → 新进程加载 checkpoint
    → 异步、压缩、副本等优化减少部分成本

    推理：
    重启加载权重并重建 KV
    → 已有方案把 KV 保存到外部位置
    → 恢复时仍需搬回或重建

这里的相关工作不是逐篇综述，而是在回答：“既然保存重载昂贵，已有优化有没有解决？”

写法先承认优化存在，再指出尚未消失的工作，不把现有方案描绘成没有经过优化的弱基线。

### 5.3 测量段的句子编排

Table 1 后的解释段按下列顺序推进：

1. 说明测量保存、恢复等哪些操作。
2. 给出平台、单 GPU/多 GPU 配置和 page-cache 条件。
3. 选择代表性训练结果。
4. 选择代表性推理结果。
5. 总结即使优化后，保存和恢复仍有显著成本。

表格给完整比较，正文只选服务于判断的数字，不逐格复述。

本块证明的是“现有恢复值得进一步改变”，还不是证明 Anchor 已经获得某个端到端收益。故障比例与单次恢复成本是两种证据，不能直接拼成未测量的服务收益。

### 5.4 第二章的动机是什么

动机不完全等于机会。第二章完成的是：

> 目标问题很常见，而且现有处理很贵，所以值得解决。

“为什么有另一条可行路径”在第三章展开。设备仍存活的事实已在第二章埋下，但尚未推导成新的 ownership 关系。

## 6. 第二章到第三章：从成本问题转向操作必要性

第三章开头是：

> Existing systems apply the same recovery method regardless of whether the GPU is actually damaged: checkpoint → restart → reload. We investigate the following question: if a shallow disruption occurs, can we handle it in a better way?

两句分别回收现状和提出新问题。

这里的转向是：

    第二章问：恢复要花多少成本？
    第三章问：在浅故障中，是否还必须进行同样的恢复操作？

重复 checkpoint/restart/reload 是有意义的，因为第二章用它描述工作，第三章用它质疑这项工作的必要性。

这一承接也避免了“测到慢 → 宣布新系统”的跳跃。作者先检查什么条件让旧路径显得过重，再提出设计。

## 7. 第三章第一块：机会与根因

### 7.1 第一个自然段：机会来自新进程落在哪块 GPU

关键句：

> There is a key difference between the two: which GPU the new process lands on.

内部顺序：

    表面恢复流程相同
    → 新进程的物理落点不同
    → destructive failure 要换节点
    → shallow disruption 设备和 OS 仍在
    → 已有系统能够原地重启
    → 已避免节点重分配和环境重初始化

这段承认 in-place restart 已被使用。Anchor 要利用的是这个条件尚未兑现的另一部分价值，不将原地重启本身归为自己的创新。

块内没有先介绍 daemon。读者首先要理解机会的物理基础：相同设备仍可使用。

### 7.2 第二个自然段：解释为什么机会没有自动兑现

原文首先给可见的浪费：

> the checkpoint mechanism first saves data out of the GPU and then loads it back onto the same GPU.

随后四步：

| 句子职责 | 内容 |
| --- | --- |
| 提出疑问 | 同一 GPU 上的数据为何必须先移出再移回？ |
| 解释现有必要性 | 进程退出导致 GPU 内存被回收 |
| 下探关系根因 | CUDA context 拥有内存，对象命运与 context 绑定 |
| 推出设计要求 | 使用对象的原 context 退出后，相关内存应能继续存活 |

这一段同时避免两种误解：不是说 checkpoint 毫无作用，也不是说仅靠原地重启就能自动保住数据。

### 7.3 本块输出

输出是“需要什么能力”，不是完整系统：

> 内存对象的存活不应必然取决于易失败 worker 的存活。

下一块自然回答：怎样改变这种关系？

## 8. 第三章第二块：核心见解与实现可行性

原文开头：

> Our key insight is: we should decouple memory ownership from the worker process.

它直接回答上一块的设计要求。此时 ownership decoupling 不再是凭空出现的术语，而是修复生命周期绑定的具体方向。

随后 IPC 的两个性质各承担一个任务：

| 性质 | 读者问题 | 原文中的解释路径 |
| --- | --- | --- |
| 保留引用支持对象存活 | worker 退出后为什么不会丢失内存？ | 共享引用 → worker 退出 → 仍有 context 持有 → 对象继续存活 |
| 虚实映射支持直接访问 | 使用者如何访问另一个 context 持有的数据？ | 建立映射 → 硬件地址转换 → 映射后直接访问 |

这里按原文的机制叙述分析其作用，不将该段写作分析当作独立的 GPU IPC 语义验证。

“零开销”需要按其上下文理解：原文论证的是映射后的访问路径，不是整个 Anchor 的管理、初始化和一致性协议全部没有开销。

小节最后把性质合起来：由另一个进程继续持有内存，worker 的浅故障就不必摧毁这份状态。

本块结构是：

    关系变化
    → 已有硬件机制
    → 存活性质
    → 访问性质
    → 核心方向可行

下一块回答的不是“为什么能”，而是“一次实际执行怎样发生”。

## 9. 第三章第三块：用单个 tensor 演示完整时间路径

§3.3 的标题限定了认知范围：

> Anchoring a Single GPU Tensor

它选择一个对象，而不是一次性展示整个框架。

| 顺序 | 叙述内容 | 句子目的 |
| --- | --- | --- |
| 1 | 说明演示单个内存对象 | 控制本段范围 |
| 2 | daemon 与 worker 各有 context | 建立角色与边界 |
| 3 | daemon 代替 worker 分配 | 指出 ownership 在哪一步改变 |
| 4 | IPC 给 worker 访问权 | 分离持有与使用 |
| 5 | worker 正常执行 kernel | 解释正常路径保持在哪里 |
| 6 | worker 退出，daemon 仍保留对象 | 验证生命周期变化 |
| 7 | 新 worker 映射同一内存 | 闭合恢复过程 |
| 8 | 推广到大规模工作集 | 回到第二章的大状态代价 |

§3.2 和 §3.3 因而不是重复：

- §3.2 按性质解释可行性；
- §3.3 按时间演示可执行性。

读者读完后能在脑中回答“谁分配、谁持有、谁执行、谁在故障后继续存在、谁重新接入”。

但单对象示例不证明完整应用已经正确恢复。这个能力边界就是下一块的入口。

## 10. 第三章第四块：最小机制留下哪些真实系统缺口

原文承接：

> The mechanism above shows how to anchor a single GPU memory object. We extend this idea to a real ML system in §4, addressing two challenges.

第一句回收已经完成的事情，第二句明确尚待完成的扩展。

### 10.1 身份挑战

    daemon 持有低级对象
    → framework 创建逻辑 tensor
    → 重启后必须恢复正确对应
    → 按 allocation order 匹配看似自然
    → 用户修改代码会改变顺序
    → 需要稳定且兼容动态对象生命周期的身份方案

本块最后停在设计要求。第三章这里不展开 access path/BFS；这些细节由第四章解释。引言提前概述过机制，不意味着第三章必须再次完整概述。

### 10.2 一致性挑战

    daemon 持有对象
    → worker 仍然正常写它
    → 中途退出留下 partial update
    → 字节存活不等于合法状态
    → 恢复需要语义一致的恢复点

两个挑战都来自核心方案：

- 跨进程保留物理对象，要求重新识别身份；
- 跨故障保留可写内容，要求处理部分更新。

挑战不是根据已有组件名反推的功能宣传。

## 11. 第三章到第四章：从设计要求到职责地图

第四章开头说先给 overview/workflow，再介绍 Rebinder 和 Consistency Guard。

读者在第三章已知道为什么需要身份和一致性，因此第四章可以直接命名对应机制。roadmap 的作用是建立：

    身份挑战 → Rebinder
    一致性挑战 → Consistency Guard

第四章不需要再证明 shallow disruption 常见或 checkpoint 很贵。它在新的层次上展开问题。

不过每个组件小节仍可用一两句重述本节目标，这是必要的局部提醒；不能把“不要重复”理解为读者必须记住所有前文细节。

## 12. 第四章第一块：总览只给职责地图

本块对应 §4.1 前部。原文先列四组件，但四组件不等于四项平行创新。

| 组件 | 本块需要说明的内容 | 当前不展开的内容 |
| --- | --- | --- |
| Allocation Proxy | worker 侧接入分配与释放 | 完整实现拦截细节 |
| Memory Manager | daemon 持有对象并维护映射 | 每一种匹配策略 |
| Rebinder | 生成身份并重新建立对应 | BFS、alias、延迟命名 |
| Consistency Guard | 提供训练/推理恢复边界 | undo/redo、metadata 协议 |

其内部编排是：

    本章兑现哪些要求
    → 系统有哪些角色
    → 每个角色在哪里、做什么
    → 后文重点展开哪两个机制

总览的输出是“谁负责什么”。读者下一步想知道“这些角色如何共同完成一次真实执行”。

不要在这一块同时要求架构图证明系统必要性、解释完整算法和展示所有性能收益。动机已经在前两章建立。

## 13. 第四章第二块：范围、入口、流程与生命周期

这一块仍在 §4.1，但和静态总览承担不同任务。它先界定哪些对象进入系统，然后按时间解释执行。

### 13.1 管理范围先于操作流程

Scope-based allocation 段依次说明：

1. 只管理需要跨重启保留的对象，如权重、optimizer state、KV pages。
2. 临时 activations/buffers 走原生分配路径。
3. 这种区分限制了额外拦截范围。
4. 用户在创建和加载这些状态的位置标记 managed_scope。

这回答了“是不是所有分配和计算都要经过 Anchor”。范围不清楚，后面的 workflow 很容易被误读为整个程序的统一路径。

### 13.2 用户示例降低采用负担

Figure 4 的代码展示初始化范围和普通训练循环。它让读者看到接入点在哪里，也明确 optimizer 实现需要配合一致性协议。

“循环代码不变”不能扩展成“整个框架零修改”。原文两者同时交代，这是准确性与可理解性兼顾的做法。

### 13.3 三阶段流程按产物依赖排列

| 阶段 | 为什么现在需要它 | 向下一阶段交付什么 |
| --- | --- | --- |
| 拦截与 placeholder | 初始化立即需要 tensor metadata，但全局命名尚未进行 | 占位对象、元信息和创建记录 |
| 身份解析与匹配 | scope 退出后判断旧对象是否存在 | 对应对象的 IPC handle |
| IPC 映射 | worker 需要访问真实驻留数据 | 可用于正常执行的 tensor |

这里可以先介绍 placeholder 的流程角色，不必立即解释它的全部内部构造。后面 §4.2 再回答为什么延迟命名、为何需要占位以及何时安全。

### 13.4 释放规则闭合生命周期

原文最后区分：

    应用释放对象 → daemon 回收
    worker 退出 → 保留需要在重启后复用的对象

这让“保留内存”不等于永久不释放，也明确 ownership 分离后的回收语义。

### 13.5 向组件一的承接

工作流已经用了“身份解析”，但只讲它发生在哪一步。读者自然会追问：身份怎样生成、为何稳定？

因此 §4.2 打开工作流中尚未展开的步骤。这种接口式承接不需要长篇“接下来我们介绍”。

## 14. 第四章第三块：Rebinder 的逐层缺口推导

本块目标是稳定地把重启后的 logical tensors 对应回 daemon 的 physical objects。

### 14.1 重新限定任务，再给真实例子

开头用 rebinding problem 重述第三章 C1。Figure 5 用普通容器中的 KV cache 表明，应用状态不一定全在框架现成的命名体系里。

例子的作用是指出覆盖缺口，不是教授 Python 语法。

### 14.2 从需求评价直观方案

原文先要求跨运行稳定 identifier，再讨论三种自然选择：

| 候选方式 | 文本指出的缺口 | 对新机制提出的要求 |
| --- | --- | --- |
| allocation sequence | 对象增删改变顺序 | 不依赖分配序列 |
| source location | 重构改变位置，循环产生多个实例 | 不把源码位置等同对象身份 |
| framework utility | 不能覆盖全部应用 tensor | 覆盖真实受管理对象 |

分析时不要把该段关于框架工具的简写扩大成完整 API 规范；写作学习点是“为什么已有覆盖范围不足”。

### 14.3 Access path 解决命名，alias 暴露唯一性要求

    Python 对象形成引用图
    → root 沿属性和容器索引到达对象
    → 路径带应用语义
    → 用路径作为标识

接下来：

    一个对象可能有多个路径
    → 需要确定选择
    → 固定 BFS/字典序并处理环
    → 第一次到达的路径成为名字

BFS 是实现确定性命名的手段，不应被孤立升级成另一项贡献。

### 14.4 正确命名之后，还必须控制命名成本

Deferred naming 段按下面顺序展开：

    路径需要从 root 向下遍历
    → 对象没有 parent 信息，不能简单向上找
    → 每次 allocation 都全图遍历很贵
    → scope exit 批量命名
    → 已释放临时对象不进入命名结果

这段每句都在推出延迟命名，未引入无关优化。

### 14.5 延迟命名引出 placeholder，placeholder 引出初始化记录

新的方案留下新的问题：

    真实对象解析延后
    → 框架现在可能需要 shape/dtype 等信息
    → 用轻量 placeholder 满足初始化需求
    → 说明其使用限制和安全条件

然后处理首次创建：

    daemon 可能没有旧对象
    → 必须知道如何初始化
    → 记录 shape-based、like-style、copy-style 创建信息
    → copy-style 的源数据可能在等待期间改变
    → 必须在合适时点保留其内容

这些细节虽然多，但属于同一条链，而不是功能清单。

### 14.6 Matching 闭合本节

最后完整列举：

    旧名字与兼容 metadata → 复用
    没有名字 → 新建
    名字相同但 metadata 冲突 → 按策略拒绝或重建
    → 返回 IPC handle
    → 替换数据指针
    → tensor 可使用

本节最后回到总览工作流中的“获得可运行 tensor”，从而闭合本块目标。

## 15. 第四章第四块：Consistency Guard 的分层方案

本块回答 C2：保留对象之后，怎样恢复到合法状态？

它内部包括通用方案、训练方案、推理方案。三者应当视为同一个大逻辑块中的层次与分支，不是三个平行系统贡献。

### 15.1 先给通用方案，形成可行性与成本参照

§4.3 开头预告通用保证和应用语义协议。§4.3.1 按执行依赖说明：

    识别即将修改哪些内存
    → 写前备份
    → 按组完成提交或失败回滚

其中组边界与未保留的中间 activations 有关：恢复单元需要能回到实际可继续执行的位置，不能任意停在某个 layer 内。

随后 Trade-offs 段：

    通用方式透明
    → 跟踪 API/kernel 行为有执行开销
    → 备份大状态有显存代价
    → 需要利用应用语义降低成本

如果删掉这个成本段，后面两种协议就像另起炉灶；有了它，轻量协议成为必要回答。

### 15.2 训练协议：定义恢复点，再寻找可重做的信息

内部推理顺序：

1. 定义训练一致状态。
2. 解释 backward/collective 与 optimizer 之间的 gradient-finalization boundary。
3. 区分边界前失败和边界后失败。
4. 引入 optimizer chunk 作为更新单元。
5. 利用 finalized gradients 在更新阶段不变的性质。
6. 用已有 gradients 重做未完成更新。
7. 指出正在更新的 chunk 可能只有部分元素改变。
8. 用单 chunk undo 处理这个缺口。
9. 说明 cursor、undo 的正常和恢复规则。
10. 用不同中断位置的 ranks 演示边界情况。
11. 回到与完整 CoW 的开销比较。

其中“观察 → 机制”最关键：

> 梯度不再改变，因此能够承担 redo 信息。

随后马上检查：

> 但当前 chunk 写了一半，直接再更新一次是否会重复修改某些元素？

这一缺口推导出 undo buffer。读者理解的是为什么需要这些状态，而不仅是记住变量名。

### 15.3 伪代码和图的不同职责

Algorithm 1 明确更新顺序，尤其是备份、发布 undo 标记、更新和推进 cursor。

Figure 6 的三种中断情况让读者检查：
- 写入中断；
- 写入完成但 cursor 未提交；
- 已完成提交。

它们使协议边界可想象，但图示本身不替代完整正确性论证或后续实验。

注意 Markdown 中 Algorithm 1 的 listing 出现在 Observation 段之前。上述十一步是逻辑依赖归纳，不应误称为原文每一对象的精确排版顺序。图表和算法的页面位置不必完全等于读者理解的推理顺序。

### 15.4 推理协议：利用盲写覆盖未提交内容

内部顺序：

    定义完成的 inference step
    → KV 新 slot 的追加/盲写性质
    → 故障会污染正在写的 slot
    → 重执行 forward 能覆盖这些 slot
    → 完成 step/chunk 后提交 metadata
    → 恢复最后提交视图，再重执行未提交工作
    → 说明 metadata 和重算成本

这里的“无 GPU 内存开销”按轻量协议新增保护内容的上下文理解，不泛化为整个系统零开销。

训练与推理共享的不是具体算法，而是设计方式：

> 从应用已有的边界和可重建性质出发，减少通用 CoW 所需保存的信息。

### 15.5 组件一到组件二的衔接

§4.2 解决“是哪份对象”，§4.3 解决“里面的内容能否继续使用”。它们共同兑现第三章两个挑战。

这种并列关系已经由 roadmap 建立，因此不需要强写“因为完成 rebinding，所以产生 consistency”。顺序上的后继不等于因果上的派生。

## 16. 第四章第五块：讨论是边界闭合，不是重复总结

§4.4 四个子块分别回收前面一个假设：

| 子块 | 前面的机制承诺 | 本块追问 |
| --- | --- | --- |
| Rebinding assumptions | 应用路径支持对象身份 | 名字、shape 相同但语义改变怎么办？ |
| Failure coverage | daemon 保留 GPU 状态 | daemon/设备失效或故障无法确认怎么办？ |
| Silent errors | 显式 worker disruption 可恢复 | 没有退出信号的静默破坏是否覆盖？ |
| Protocol scope | 应用语义降低保护成本 | 不满足 gradient boundary 或追加 KV 时怎么办？ |

各段典型编排为：

    机制依赖的条件
    → 条件不成立的实例
    → 能力边界
    → 可用替代路径或外部处理方式

这里必须区分不同 fallback 的作用域：

- general protocol 扩展的是一致性处理方式；
- checkpoint 支持超出快速路径条件的恢复；
- diagnosis/validation 面向静默错误等其他问题；
- 它们不是互相可替代的统一兜底，更不能说 CoW 解决 tensor 语义身份变化。

边界段让前面主张有明确适用条件。它不应被理解成可删的防御性清单，也不需要上升为新的贡献。

| 接缝 | 前块已经建立 | 下一块自然问题 | 承接方式 |
| --- | --- | --- | --- |
| §2.1 → §2.2 | 目标故障普遍 | 为什么恢复这类故障昂贵？ | 从事件进入恢复对象 |

## 20. 为什么内容很多，读者仍能跟上

### 20.1 每次只打开一个必要层次

第二章不提前讲 BFS；第三章不展开 placeholder；总览只给 placeholder 的流程作用；Rebinder 再解释其构造理由。相同词可以先轻量出现，之后获得完整解释。

### 20.2 先展示能力，再暴露能力边界

单对象存活成立后，才讨论全应用的身份和一致性。通用一致性成立后，才讨论成本。每个转折都让读者知道目前已经解决什么、还缺什么。

### 20.3 实现细节沿缺口出现

alias 不是因为系统里有一个 alias handler 才值得讲，而是 access path 存在多路径；placeholder 不是因为代码里有这个类才出现，而是命名延后但框架还需要 metadata。

### 20.4 相同主张在不同深度重现

- 引言：让读者先理解整体主张。
- 第二章：支撑场景和成本。
- 第三章：推导机会与关系变化。
- 第四章：解释机制与边界。
- 后续实验：验证机制和效果。

重复只有在增加解释层次时才有价值。如果相邻两个块都在做同一个总结，就应合并或让后一块开始新动作。

## 21. 用于未来写作的迁移原则

学习这三章时，应迁移以下关系，而不是章节标题和篇幅：

1. 先界定目标场景，再展示处理成本。
2. 机会来自真实执行条件，不只来自“现有方法没有功能”。
3. 从不必要操作追到造成操作必要性的系统关系。
4. 改变关系以后，用最小实例证明可理解、可执行。
5. 从最小实例的能力边界推出真实系统挑战。
6. 组件小节逐一兑现挑战，复杂细节沿新的缺口展开。
7. 讨论回收假设和替代路径，不重新发明贡献。

不能机械迁移的内容：

- 不要求每篇论文恰好两个挑战、四个组件。
- 不要求总览都放在第四章，或机会都单列第三章。
- 不要求所有方案都先展示一个昂贵的通用版本；只有真实存在这样的层次时才采用。
- 不因为参考论文提到某个硬件性质，就把它当成另一系统已验证的事实。
- 不把“只要让生命周期分离就更快”外推到不具有相同故障与状态条件的场景。

这份分析提供的是提问方式，不是对 Deferix 后续章节的自动重写方案。

## 23. 最值得保留的整体认识

Anchor 的第二至第四章不是“背景知识、系统想法、组件介绍”三份材料并排放置，而是一条连续的解释过程：

> 让读者先相信问题值得处理，再理解现有工作为什么仍然发生；随后找到能改变这些工作的系统关系，用最小执行过程展示这个改变，最后解释真实系统为此必须补齐哪些机制。

总览负责定位，工作流负责执行画面，组件负责设计选择，讨论负责成立条件。让不同逻辑块各自完成不同任务，才是技术细节很多但阅读负担仍可控制的原因。
