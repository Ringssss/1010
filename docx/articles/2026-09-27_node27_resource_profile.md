# node27 结论：ckpt 流动能否被准确建模、最小代价/最快流怎么用

日期 2026-09-24。机器 node27（8×DCU，GPU→NUMA 一一对应 {0:0,1:3,2:2,3:1,4:4,5:7,6:6,7:5}，
NVMe 挂在 NUMA0 且与 GPU0 同一个 PCIe switch/root port）。模型 = 冻结的
`V9_links_hswio_numa_rw_conflict_tied`（`model_fit_node27_frozen.json`，冻结后未再拟合）。
ckpt = Qwen3.6-35B-A3B 67 GiB（TP2 每卡 33.5 GiB，TP4 每卡 16.75 GiB）。

## 1. 一句话

**能建模，但只在"线性区"里准；而 FluidCKPT 恰好能把自己放进线性区。**
线性区 = 每个 PCIe root port 只碰一个 NUMA 节点，且没有一个 NUMA 节点同时喂多个 root port。
在线性区里，一个几十个参数的"单流上限 + 共享资源容量 + max-min 公平"流体模型，
held-out 聚合误差中位 1.0%，真实计划执行 makespan 误差 ≤5%；LP 求出的最快流计划就是真实最快的。
出了线性区（跨 NUMA 读、一个节点喂多卡、一个 port 既读 A 节点又写 B 节点），误差 10–70%，
且"在不准的模型上做最优化"会比朴素就近策略更慢。

## 2. 建模精度（held-out 列是冻结后新测的数据，噪声底 ≈0.65%）

`scripts/purity_split.py` → `purity_split_node27.json`，V9 冻结模型，聚合带宽相对误差：

| 混合流类型 | 全部数据 n | 中位 | p90 | 仅 held-out n | 中位 |
|---|---|---|---|---|---|
| root port 单节点 + 无 NUMA 扇出（线性区） | 61 | **1.1%** | 4.7% | 15 | **1.0%** |
| root port 单节点，但一个 NUMA 喂多卡 | 25 | 9.8% | 31% | 8 | 5.0% |
| 某 root port 碰 ≥2 个 NUMA 节点 | 35 | 9.0% | 33% | 25 | 9.0% |

按验证集：validation2（通用随机）中位 3.6%/p90 52%；validation3（物化形状随机）中位 9.7%/p90 31%；
validation4（冻结后按放置策略生成：本地 DRAM + P2P 一对一 + NVMe 按目标 NUMA 暂存）中位 4.4%、max 8.9%。
validation4 里含 NVMe 的混合偏高估 2–9%，就是下面第 3 节的 root-port 冲突（NVMe 写别的节点）。

## 3. 三个硬件事实（决定线性区边界）

1. **设备侧是线性的**：每卡 H2D 46–47、D2H ~45、P2P 单对 ~155、每卡 HSW 入 165/出 168/入+出 283、
   NVMe 5.8（1 流）/7.0（≥2 流）；α≈0.12–0.18 ms，R²≈1。8 卡本地 H2D 聚合 ~373 GB/s 线性叠加。
2. **root port 碰两个 NUMA 节点就塌**（本轮新发现，把旧的"远端双向冲突"推广了）：
   - GPU 自己 H2D+D2H，两边节点不同 → 每向 7–10 GB/s；两边都是本地节点 → 37.7+37.7（只受内存读写预算 75 限制）。
   - GPU0 与 NVMe 同 port：h2d n0→g0 + NVMe 写 n0 → 46.2+5.9（不冲突，"switch 带宽不足"假设被否定，
     V10 拟合也没给 `pcie_sw` 任何容量）；h2d n0→g0 + NVMe 写 n2 → h2d 掉到 **29.5**；
     h2d n2→g0 + NVMe 写 n2 → 45.5+5.8（同节点，不冲突）。见 `profile_node27_train3.json`。
3. **一个 NUMA 节点喂多卡是路由相关的**：NUMA0→两卡 57–90 GB/s 视卡对而定，不是一个容量数能描述的。

## 4. 真实执行：计划 × 场景（每个计划新进程、3 次取中位，`plans_node27*.json`）

单位秒；"误差" = (预测−实测)/实测。

| 场景 | NVMe-only | 就近最快源 | 无约束 LP | **线性区 LP** | 线性区 LP 误差 |
|---|---|---|---|---|---|
| tp4_from_running_copy（HBM 副本在 4–7） | 10.35 | 0.117 | 0.188 | **0.117** | +1.1% |
| tp4_numa_local_dram | 10.33 | 0.392 | 0.482 | **0.393** | +2.3% |
| 4xtp2_numa_local_dram（整机 8 卡 268 GiB） | 41.41 | 0.777 | 1.044 | **0.767** | +1.5% |
| 2xtp2_clone_from_one_running（一个运行中 TP2 克隆两份） | 20.66 | 0.440 | 0.391 | **0.290** | −5.1% |
| tp2_scattered | 10.45 | 0.844 | 0.793 | 0.831 | −1.5% |
| 4xtp2_from_two_dram_copies（副本放错节点） | 41.29 | 1.279 | 1.862 | 1.288 | −25%（区外） |
| tp4_nvme_plus_far_dram（副本放错节点） | 10.35 | 1.047 | 1.284 | 1.048 | −8%（区外） |

复现性：独立重跑（`plans_node27_linear_replicate_v10fit.json`）clone 0.284 s、其余差 <3%。

要点：
- **线性区 LP 在所有场景都不差于就近策略（差异在 1% 噪声内），且预测准**；在有多个互补源的场景（clone）快 34%。
- **无约束 LP 在 5/7 个场景比就近策略慢**（最多慢 60%）：它把 NVMe、跨节点 DRAM 当"免费的额外带宽"加进来，
  而这些恰好让 root port 碰两个节点。模型不准时，优化器会系统性地利用模型的错误。
- **pacing（按 bytes/T 限速）在线性区把实测钉在预测上**（多个场景误差 0.0%），在区外无效。
- work-stealing 动态执行（`dynamic_*`，按 LP 偏好拉 chunk）不稳定：2 个场景比线性区 LP 快 1–3%，
  5 个场景慢 5–72%——它会用到所有候选路径，包括区外路径。先划线性区、再动态，是后续可做的组合。
- **NVMe 在有 DRAM/HBM 副本时几乎没有增量价值**（7 GB/s vs 每卡 47/155），反而容易破坏 port 纯度；
  它的价值是"最后一层"：NVMe-only 恢复整份 67 GiB 约 10.3 s（NVMe 总共 7 GB/s），
  同样 67 GiB 走本地 DRAM（TP4）0.39 s（26×），走 HBM P2P 0.117 s（88×）。
- 最小代价第二阶段（少借服务中卡的 HSW、少用远端 DRAM，T ≤ 1.1·T*）：全本地场景里最快与最省是同一个解
  （4xtp2_numa_local 0.792 s）；clone 场景里是真实权衡——少借服务中卡的 HSW，实测从 0.29 s 变成 ~0.36 s。

## 5. 对 FluidCKPT 设计的直接含义

1. **降级（demotion）写本地**：HBM→DRAM 时写到该卡自己的 NUMA 节点。这一条就保证了下次物化在线性区。
   本机 GPU↔NUMA 一一对应，所以"本地"是唯一的。
2. **一个 port 不混节点**：demote（D2H）和 load（H2D）同时发生在一张卡上时，两边必须是同一个节点，
   否则两个方向都掉到 7–10 GB/s。NVMe 暂存缓冲放在 NUMA0，且只直喂 GPU0。
3. **规划器 = 线性区内的最快流 LP**（`plan_lp_linear`），区外路径只在没有其它非 NVMe 源时作为单路兜底，且不拆分。
   预测 makespan 可以直接当 SLO 用（线性区 ±5%）。
4. **执行 agent 短命、只看自己的卡**：长寿 worker 在 ~200 次 setup 后 P2P 从 155 掉到 20（`diag_*`），
   新进程 + 只可见自己的 GPU 就没有这个问题。
5. **HBM 副本优先**：P2P 一对一 155、一源喂两卡各 ~81（模型准确预测），是 DRAM 的 3×。
   "一个运行中实例 + 本地 DRAM" 组合（clone 场景）靠 LP 拆分，0.29 s 克隆出两份 TP2（共 134 GiB）。

## 6. 还不知道的

- 跨机（node29 等）、RDMA/NAS 路径没测，需要用户确认后再做。
- 服务中卡同时做 TP 通信时，被借用的 HSW 端口对推理延迟的影响没测（min-cost 里的 p2p 代价 1.0 是假设值）。
- NUMA 扇出（一个节点喂多卡）的路由相关性没有建模，只是在规划里规避。
- 只在 node27 一台机器上测过；root port 拓扑（哪张卡和 NVMe 同 port）要按机器从 sysfs 读。
