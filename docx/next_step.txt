8. 一旦有什么疑惑就去搜索相应的代码，当我们感到盲目的时候就去收集信息。
9. 在你添加进展的时候，把【本轮命令】也加进去，让我们知道这次信息的指令是什么。
10. 并不是每一次都需要在code_building/process_docs新建一个文件，大多时候只需要写在上一个进度文件中即可，只有任务主题进入下一阶段了，我们才需要新建一个新的文件。
11. 具体代码建设委派子agent，主agent审查验收；按用户最新约定使用gpt-6.1-sol/high，替代历史sonnet约定。详见根目录AGENTS.md。
12. **禁止使用 inline script（`python3 -c "..."`）跑实验。** 所有实验必须写成独立的 `.py` 脚本，保存在 `codex_coding/src` 对应子目录下。原因：inline script 跑完即丢失，无法复现、无法归档、无法在过程文档中引用。过程文档中的命令必须是 `python codex_coding/xxx.py`，不允许出现 inline code block。
13. **控制变量 debug 原则**：遇到 bug 不要猜机制，要找变量。列出所有能跑和不能跑的 case，找到 PASS→FAIL 之间变化的那一个因素，然后设计实验只改变那一个因素。优先排除而非猜测。直接 printf 输出具体数据（地址、值、索引）是最好的工具 — 不要靠脑补推理，让数据说话。
14. **画图文件组织**：模版在 `codex_coding/cite_plt_coding/plt/`（只读参考，禁止覆写）。画图源代码放 `codex_coding/src/plt/`，输出放 `codex_coding/results/plt/`。需要嵌入论文的图拷贝到对应论文项目的 `figures/` 目录。画图脚本的数据输入部分必须有清晰注释（数据来源、含义、单位），确保之后回来能直接看懂。
15. **开发编号规则**：通常每个新开发轮次（含上下文恢复）将`vX.Y.Z.N`最后一位加1；但用户显式指定编号时以用户指示为准。**当前有效例外：保持v0.1.23.3/task2，在用户再次明确指示前不得改变。** 2026-10-23归档时按用户既有指示和AGENTS纠正此处遗留的.2，不是开发编号递增。
16. **核心库与脚本分层原则**：会被 `import` 的产品代码（推理引擎、核心部件、库本体）放 `main_lib/`；`codex_coding/src` 只放"为了验证/测量/诊断而跑"的脚本。判据一句话：**会被 import 的进 main_lib，跑一次看结果的进 codex_coding/src。**
17. **core dump 防护**：本机 `kernel.core_pattern=core`、`core_uses_pid=1`，且内核对每个崩溃进程 dump 整个显存
    （单节点 8 卡 = 8 个 18–22 GB 文件）。**跑任何会让 GPU 进程崩溃的实验前，必须在 launcher 里加
    `ulimit -c 0`**，否则一次崩溃即可写满 `/home`（2026-09-27 已发生，203 GB）。
