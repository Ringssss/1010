# FLUIDCKPT —— 项目范围与定位

日期：2026-09-27（`v0.1.23.1`）
状态：立项依据（`cites/` 首篇）

## 1. 要解决的问题

大模型（本项目以 GLM-5.3 为目标，703.7 GiB、tp_size=16）从「进程不存在」到「可以服务」
的冷启动时间是分钟级。其中绝大部分不是权重 I/O，而是进程启动、框架 import、
CUDA/HIP context 构建、分布式初始化、以及权重从磁盘到 TP shard 的解码与量化（见
`articles/2026-09-27_glm53_startup_vmfault_forensics.md`）。

现实中的模型切换需求却是秒级的：A/B 测试、多租户、故障转移、训练-推理交替。
一次切换付几十秒到几分钟的脚手架代价，是不可接受的。

**问题定义**：如何让一个已经加载并后处理完毕的模型实例，在多节点集群中作为**可流动、
可保活的对象**存在，使任意节点都能在远低于冷启动的时间内把它「拉起来」？

## 2. 为什么这个 POC 收敛到这里

三条边界把范围收窄了：

1. **不走 NVMe 刷盘**。本地 NVMe 只有 2.5 GB/s，NFS 只有 0.27 GB/s（I10）。
   703.7 GiB 走 NFS 是 47 分钟级，走本地 NVMe 也要 5 分钟级。所以「保活」必须在
   **DRAM/HBM** 层做，SSD 只作为无其它副本时的兜底。
2. **不修改推理引擎源码**。SGLang 在本环境是厂商深度定制版本，改动源码会让结果无法
   与官方行为对比，也会随版本升级失效。因此采用 **import 期 hook**（利用 spawn 的
   re-import 语义，I8），在不碰源码的前提下接管模型加载路径。
3. **只用集合通信**。本 fabric 的跨节点 send/recv 不可用（I2），所以流动规划必须建模成
   集合通信问题——这正好与本项目的核心算法（多源多汇 max-flow）契合。

## 3. 核心抽象

**模型实例 = 一组可寻址的存储对象 + 一份派生属性清单。**

- 存储对象：每个 TP rank 的每个参数/buffer，用 HIP IPC handle 标识（I7），零拷贝共享。
- 派生属性：post-processing 产生的、无法从结构推断的量（如 MLA 的 `w_kc`/`w_vc`），
  由 capture 侧记入 manifest，restore 侧回填。

**流动 = 带容量约束的 max-flow。** 每条边是一段真实测量的带宽（I3, I11），
每个 rank 是一个 sink 有确定需求，keeper 是中间节点。

## 4. POC 的边界

**做**：
- 三节点（node27/28/29）keeper mesh 的保活与跨节点流动，端到端计时。
- 与 SGLang 自身保活机制的对比（判据：restore 到可用状态的时间）。
- max-flow 规划器与真实执行的吻合度验证（预测 vs 实测）。

**不做**：
- 修改 SGLang / vLLM 源码。
- 训练态权重、LoRA 热插拔、多租户调度策略。
- 生产级容错与安全性（用户为本机数据仓库管理员，明确「安全问题先不管」）。

## 5. 判据

**全面胜过 SGLang 自身的保活。**

具体可比量：

| 量 | 说明 |
| --- | --- |
| restore → `fired up` 时间 | 主判据 |
| 每张量固定开销的摊薄倍数 | 机制判据（I1：bucketing 27.8×） |
| 引入的额外 HBM 占用 | 成本判据（I7：IPC 零拷贝，0.01 GiB） |
| 对模型/引擎版本的侵入度 | 工程判据（零源码改动） |

## 6. 当前状态

技术线被平台缺陷阻塞：GLM-5.3 在 gfx936 上无法启动（I5），根因在 SGLang 自家 NSA path 的
`lightop_attention.fuse_layernorm_rotary_embedding`，**与 FluidCKPT 无关**（已用纯 SGLang 复现）。
应对：先用平台可启动的模型（Qwen3.6 已验证）打通全链路取得端到端数字，
GLM-5.3 可用后直接换模型。
