# FluidCKPT：论文主张、组件成熟度与最小证据链

日期：2026-10-04。本会话实现编号保持 v0.1.23.2。本文为定位与证据审计，不覆盖其他会话的实验计划或编号。

## 1. 当前能说什么

完整 GLM-5.3 的三节点 DRAM 保活、权重释放和同计算布局恢复已经通过。运行时权重 784,208,680,448 bytes，恢复后全量 SHA256 和原生参考输出一致；释放 1.471650 s，恢复请求至首 token 11.452932 s。首次准备及生成后的 SHA 不计入该恢复窗口。

其后的真实 GLM/Qwen 切模没有通过：Qwen 分配权重时 HIP OOM，控制器随后在等待导出 1800 s 后报告超时。IPC 对照退役后，worker0 的目录 HBM 为 0，但 torch 活跃分配仍为 49,080,151,552 bytes；设备 free 仅约 12 GiB。这不是三节点闭环成功。完整运行记录在 codex_coding/results/glm_roundtrip/full_distributed02，roundtrip_result.json 与失败 lifecycle 的 summary.json 分开保存。

适配 HIP IPC 的三个正确命中为 1.733868/1.362555/1.363223 s。这些值不证明出口回收正确，也不是未经修改的官方 daemon 成绩。probe_ipc_reclaim.py 在同一运行环境的独立进程中复现：复用一次导出供三次导入，释放后仍留 64 MiB；每次重新导出则最终归零。probe02_run_environment 有原始结果。新脚本按每次请求重新导出，导出 RPC 纳入请求计时；worker 退役设置本设备、收集 IPC 并释放 allocator cache，补充 reserved 指标。完整模型的新版本尚未验证，旧数据没有被改写成新版本成绩。

## 2. 三个组件的实际状态

| 组件 | 已实现与证据 | 写成论文贡献前仍缺什么 |
| --- | --- | --- |
| 权重对象与副本生命周期 | 处理后 layout/alias、精确覆盖、lease、先发布后退役、独立 CPU owner；完整 GLM 字节及生成验证 | IPC 退出物理回收复验；三节点真实双模型闭环；明确进程/owner/节点故障承诺；SSD/page-cache 总账 |
| 放置与迁移决策 | joint/multi_joint、自动候选、NUMA/共享容量、managed 控制路径；managed04 完成 Qwen 单目标闭环 | 当前 GLM 是固定布局；managed 主路径仍限定 DRAM/HBM 和单模型互斥目标场景，不是多模型三层时域联合优化；不可移动底本与可迁移块的闭环需统一 |
| 多源恢复执行 | 资源 LP、跨节点传输、prepare/execute/publish、warm engine；完整 GLM 恢复 | 不同计算布局的完整 GLM 恢复；双向让位/进入竞争；真实并发服务干扰；实际执行器与成本模型一致性 |

schedule_block_moves 是固定目标布局的贪心可行顺序，不能写成最优迁移 MILP。旧 placement01 的搬运减少约 7.8%、加载窗口减少约 15%，仅各一次样本，底本和建布局开销另计；不足以证明普遍优势。三组件有代码和局部验收，尚未构成三项已验证科研贡献。

## 3. Motivation 与可证伪主张

推荐工作主张：在固定集群资源预算下，联合管理不可变、已物化权重的保存位置、可执行迁移过程和恢复路径，以降低空闲模型 HBM 占用，并让更多模型满足让位与恢复时限。

矛盾一：HBM 常驻恢复很快，但权重长期占用可供 KV、活跃模型和工作空间使用的容量。用户需要保留的是可接受的返回成本，不能把永远占住原卡当作唯一保活形态。

矛盾二：总内存有余量不代表权重来得及恢复。副本在哪个 NUMA、哪条 NIC 后面、是否共享 PCIe 入口以及最慢 TP rank 的必需字节在哪里，共同决定恢复时间。容量命中率本身不充分。

矛盾三：最终布局可行不代表迁移过程可行。最后一个快速副本在新副本完成之前不能丢；迁移同时消费目标空间、源读带宽、暂存和前台服务资源；需求可能在迁移中反转。

最有价值的候选 insight 是：**缓存价值取决于它缩短多少恢复关键路径，并且这种收益必须通过容量可行、允许中途召回的布局变更兑现。** TP 互补性使收益非简单逐字节相加：两 rank 都要 10 秒时，只把其中一个降到 2 秒不会把模型 ready 降到 2 秒。这里的数字是解释性例子，不是实验结果。

目标采用约束或 Pareto 曲线：给定让位、恢复、前台服务要求和各层预算，最小化空闲权重 HBM（也报告 GiB·s）；或固定预算，最大化按时完成的真实恢复请求/可服务模型数。不存在可行解时如实报告；不靠取消服务要求取得零 HBM。

本地 HBM 命中应允许 Fluid 走 IPC 快路径。三节点 DRAM 加载不会凭空消除搬运；论文无需声称每一种条件都压过零拷贝。收益区域应由容量压力实验测出，并保留无收益区域。

## 4. 从功能到因果证据的顺序

1. 先修并复验物理回收。B 真正拿到空间、生成正确，才确认让位完成。GLM 的 730 GiB CPU 快照保留，不能为排错重启 owner 丢掉它。
2. 完整三节点轨迹：A→B→压力迁移→迁移 25/50/75% 召回 A→B→最终 A。记录每次目录、物理释放、内容覆盖、迁移流量和 token；本地返回与不同计算布局恢复分开验收。
3. 容量曲线：相同每卡 HBM、每节点/NUMA DRAM、SSD 和 page-cache 政策。覆盖 A+B 可以同时常驻、仅可常驻一个、仅本地 DRAM 受限、全局 DRAM 受限四类。GLM TP16 的另一计算目标是另一设备组，不能只换 HTTP 请求入口就宣称远端服务迁移。
4. 联合管理消融采用 2×2：简单放置/联合放置 × 简单来源选择/资源 LP，再比较相同分块下的串行、盲目并行和资源约束迁移。共享数据格式、搬运内核、预算、块大小和预热，避免把后处理缓存收益全部归给 MILP。
5. 独立负载发生器在真实搬运期间持续请求 B，统计吞吐、TTFT、TPOT、SLO 违约；当前脚本的块间请求样本不能当作并发干扰实验。正式尾延迟需要有依据的样本量，单次/三次样本只用于功能或探索。
6. 报告首次捕获、建布局、验证、维护和重复切换总账；统计每个 immutable epoch 的重复 D2H/磁盘加载次数，测回本和无收益区。需求翻转和迁移失败必须保留旧覆盖、可恢复或明确冷加载回退。

论文首批图：物理 HBM/DRAM/SSD 与模型状态时间线；同预算的模型数量—恢复 SLO 曲线；联合放置/流量 2×2 消融；迁移进度—召回延迟；前台 SLO 与实际迁移字节/回本。三节点足以产生初步机制证据，集群规模泛化需要更大实机或由实测校准且明确标注的仿真。

强基线至少包括适配并固定版本的 daemon HBM 命中、SGLang 本地 CPU 备份、使用同样分块和传输实现的简单集群分层缓存、联合系统。官方 CPU 备份当前 Qwen 二次恢复失败，不能把该适配失败记成对手无限慢。实现论文算法的移植基线与官方实现必须标清。

## 5. 与已有工作的边界

- [SGLang 官方路线图](https://github.com/sgl-project/sglang/issues/33522) 已包含 peer copy、跨节点填充、Mooncake 后端与容量回收等方向。路线图不是所有能力均已验收，但足以否定“只有我们想到远端”这一论据。daemon 原本就独立于 engine，不能把 engine 退出后仍有权重说成我们的独有能力。
- [ServerlessLLM，OSDI 2024](https://www.usenix.org/conference/osdi24/presentation/fu)：多层 checkpoint 加载、迁移、启动时间感知调度。对照必须允许合理的位置选择；固定目标设备组需要外部约束理由。
- [BlitzScale，OSDI 2025](https://www.usenix.org/conference/osdi25/presentation/zhang-dingyan)：计算网络供给、网络优化扩散、按层承担计算。远端取权重、少量 host cache、按层重叠不足以独立支撑新颖性。
- [PPC/MAIO，FAST 2026](https://www.usenix.org/conference/fast26/presentation/liu-yubo)：可编程 page cache、I/O 模板、亲和性、预取回收。不能把改 Linux cache 本身当成新贡献；先统一 page cache 容量和实测缺页/I/O，确认用户态控制无法解决的缺口再考虑内核修改。

上述比较基于官方介绍与已读本地分析，是选题审计；完整相关工作排重还应精读全文和实现。MILP、最大流、HLL、NUMA 优化各自都是工具；论文贡献是新约束或耦合导致的决策改变及其实测收益。HLL 对三节点正确性目录没有必要，最多未来用于可合并的需求统计。

## 6. 投稿定位

当前优先按 FAST 的存储系统故事打磨：已物化权重生命周期、容量与恢复折中、最后快速副本迁移、跨层/跨节点资源账本。FAST 官方 CFP 明确包含 memory hierarchy 和 memory-only storage，所以不需要为了会名强加内核改动。

OSDI 同样覆盖存储和 ML 系统；若主要贡献扩展成与服务调度协同的通用运行时接口、可抢占恢复和前台 SLO 隔离，并在工作负载中体现广泛意义，也适合 OSDI。两者按贡献选择，不能把 FAST 视为证据不足时的低标准替代。

截至 2026-10-04，[FAST 2027](https://www.usenix.org/conference/fast27/call-for-papers) 秋季截稿 2026-09-15 AoE 已过；[OSDI 2027 初步 CFP](https://www.usenix.org/conference/osdi27/call-for-papers) 为 2026-12-01 摘要、12-08 全文。时间表不是质量承诺，也不能据此假设 FAST 2028 未公布日期。
